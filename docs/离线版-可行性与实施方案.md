# 离线版可行性与实施方案（2026-11-10，v2 修订）

> **结论先说**：离线版**技术上可行**，但不是「重新打个包」——它要求把 Python 服务端
> 的编排层（`web/dushan_server.py` 3286 行，其中 `Session` **1528 行 / 42 个方法**）
> 在 Rust 里重建，并在设备上跑推理。本轮**未**交付可用的离线 APK；本文给出
> 实测数据、缺口清单、分阶段方案与验收口径，供你决定是否继续投入。
>
> 同轮已交付：联网版 APK v1.1.0（沉浸全屏 / 5 分钟亮屏 / 幺鸡图标 / 允许小窗）。
>
> **v2 修订（同日，读代码后）**有三处判断变化，工作量比 v1 估算**下降约一半**：
> 1. Rust 的 `Game` 是**完整**状态机（`new_with_wall` 可从洗好的牌墙开局，
>    `legal_actions`/`step` 覆盖摸打碰杠胡全流程，**且独山麻将无定缺阶段**），
>    所以"移植 1528 行编排"实际是"写会话循环 + JSON 视图"，不是逐行翻译；
> 2. 前端可以**一字不改**——在 APK 内起一个 127.0.0.1 的本地 HTTP 服务，
>    把同一份 `dushan.html` 与同名 `/api/*` 路由原样提供出去，WebView 指向它即可；
> 3. 推理后端**不必**捆 ONNX Runtime（见 §3.2），纯 Rust 的 `tract` 能省掉 17.6 MB
>    的 `libonnxruntime.so` 与 JNI 打包风险。

## 1. 为什么「把网页打进去」不够

现有客户端（`tauri-app/`）是**局域网直连**：Rust 侧只做「记地址 / 探连通 / 导航」，
游戏页面、规则、AI 全在你电脑的服务端。离线的本质是**把那台电脑搬进手机**。

| 层 | 现状 | 离线需要 |
|---|---|---|
| 前端页面 | `web/static/dushan.html` 582 KB，零依赖 | 直接复用（**不用改**） |
| HTTP 接口 | 16 个 `/api/*`，`/api/state` 单次 32 个顶层字段 | Rust 里实现同构接口 |
| 对局编排 | Python `Session` 1528 行 / 42 方法（轮转、碰杠胡响应窗口、鸡账、报叫、抢杠、同轮跟打、结算入账） | 在 Rust 写会话循环（状态机已有，见下） |
| 规则/结算 | Python `zhuoji/dushan.py` 1607 + `rules.py` 711 | **Rust 已有**：`state.rs` 1005 + `settle.rs` 1140（已与 Python 逐位对拍） |
| 搜索 | `rust_engine/src/{search,deep}.rs` | **Rust 已有**（热路径）。网络前向由 `take_batch()/feed()` 协议外挂，后端可换 |
| 网络推理 | PyTorch / ORT（macOS CoreML） | 纯 Rust `tract`（首选）或 Android ORT |
| 讲解/听牌 | `zhuoji/reason.py` 395、`ting_*` | 需移植或降级 |

**已有资产比想象中多**：规则、结算、编码（v1/v2/v3）、搜索骨架、determinization 全在 Rust，
`annotate` 二进制已经用 ORT 跑前向（`rust_engine/src/infer.rs`，`ch/gdim` 可配 15/70 与 63/130）。
更关键的两点：

- `Game::new_with_wall(wall, dealer, cfg, ft)` 支持**从任意洗好的牌墙开局**，
  `legal_actions(t)` + `step(a, t)` 覆盖摸打碰杠胡全流程，`Outcome` 走 `settle.rs`。
  **独山麻将没有定缺阶段**（`grep 定缺 zhuoji/dushan.py` 无命中，`state.rs` 的
  `phase` 只有 `DISCARD/SELF_KONG/RESPOND/OVER`），所以开局后不存在"等玩家选缺门"这类状态，
  会话循环比预想的短。
- `Search` 的网络是**外挂批协议**：`needs_net()` → `take_batch()` → 外部算 → `feed(actions, values)`。
  这意味着设备端只需要实现「一批编码张量 → 一批 Q」，搜索档与贪心档**共用同一段代码**。
**缺的是「会话循环 + JSON 视图 + 设备打包」**，不是「从头写一个麻将」。

## 3. 三个必须先解决的技术风险

1. **设备端推理速度未知（最大风险）**
   手机是 CPU/NNAPI，不是 ANE。同机（M 系列，空载，v3 编码）实测：

   | 模型 | 参数 | 贪心单步 | N32 单步 | ONNX |
   |---|---|---|---|---|
   | `dushan_master`（v1 编码） | 0.769M | 0.66 ms | — | 2 MB |
   | `champ_exit_p48` | 9.8367M | 4.5083 ms | **1.8111 s** | 37.5 MB |
   | `slim_s`（E-SLIM 学生） | **0.8141M** | **0.9211 ms** | **0.2749 s** | **3.1 MB** |

   手机大核通常比本机慢 2–4×。⇒ **贪心档全程可实时**；P48 的 N32 在手机上会是
   **5–10 s/步**，一盘几十步 = 数分钟，**不可用**；而 `slim_s` 的 N32 上手机约
   **0.6–1.1 s/步**，是**唯一在手机上可能可用的搜索档**。

   **建议据此调整模型清单**：原需求「只保留 master 和 P48」在离线场景下不划算——
   P48 独占 37.5 MB 体积、且它的搜索在手机上跑不动，只能当"思考档/讲解"；
   而 `slim_s` 3.1 MB 就能提供可用搜索。**推荐包内带 `master` + `slim_s`（模型共约 5 MB），
   P48 不带**；若坚持要 P48，包体 +37.5 MB，且它的搜索档只能标注"等 5–10 秒/步"。

   **定稿（2026-11-10 19:0x，用户口径「slim_s 给 web 并给离线版」）**：
   `slim_s` 已作为 `champ_slim_s` 注册进线上（`models/champions.json`，只增不替），
   并导出按 stem 隔离的 `models/onnx/champ_slim_s.onnx`（3.3 MB，enc 3 / 63-130，四头齐，
   `tools/export_onnx_cache.py` 四项校验 PASS）。离线包直接复用同一份权重与 ONNX，
   **不另存一套文件**，避免线上/离线数值分叉。统计依据见
   `reports/E-SLIM-学生瘦身.md`（闸门 A 非劣 p=1.35e-05；字面 TOST 双侧因"显著更好"
   不成立，已登记为预登记措辞缺陷）；独立池复现与 vs P48 直接对打见
   `runs/gates/slimB_*`。

   **主力选谁：用 `slim_s`，`master` 降为后备（2026-11-10 23:3x，据追测矩阵更新）**

   同池（`7_400_000`）四臂实测把这件事钉死了：

   | 谁是 AI，对手都是 master+N32 | 分差 |
   |---|---|
   | `slim_s`（0.82M，贪心） | **+0.855 ± 0.266**（600 seed） |
   | `champ_exit_p48`（9.84M，贪心） | +1.946 ± 0.402（300 seed） |

   ⇒ 学生**只走贪心就胜过开了搜索的 master**，且它贪心单步 0.9211 ms（`master` 0.66 ms 同量级）、
   N32 0.2749 s。因此离线版对局 AI 的推荐顺序是：

   1. **主力 = `champ_slim_s` 贪心**（默认档，手机上实时）；
   2. **搜索档 = `champ_slim_s` N32**（约 0.6–1.1 s/步，桌面节奏可接受）；
   3. **`master` 只作后备/回退**（2 MB，v1 编码 15 通道，与学生的 v3 两套张量，
      同时带会让 `annotate` 侧要两套编码分支——若包体紧张，**可以只带学生**）。

   附带一条量化事实：`master` 打开 N32 搜索 ≈ 白拿 **3.0 分**（同池配对差
   +2.997±0.551）。这说明手机上若跑不动 P48 的搜索，用学生的 N32 才是把"搜索红利"
   搬到设备的唯一现实路径。

2. **推理后端选型：`tract` 优先，ORT 兜底**
   - `tract-onnx` 是纯 Rust、无动态库、交叉编译到 `aarch64-linux-android` 干净（不碰 JNI/`loadLibrary`），
     编译后约 +2–4 MB，**能省掉 17.6 MB 的 `libonnxruntime.so`**；
   - 代价是数值与算子覆盖需要验证：本仓库的网只用到 conv/bn/relu/add/linear/softmax/SE 池化/dueling 拼接，
     属于 tract 的成熟算子，风险低但**必须过 §3.3 的逐位对拍**；
   - 若 tract 在某个算子上失败或慢于阈值，退回 `ort` + Android AAR（已验证 Maven 可下载、ABI 齐全，
     属**确定性工作**，非未知）。
3. **JSON 契约必须逐字段一致**：前端对 `phase/pending/players/events` 的字段名与语义敏感。
   对策：拿现网服务端做**黄金样本**——同一 seed、同一串动作，两边回放后逐字段 diff，
   差异为 0 才算通过（与 `rust_engine` 已有的 `parity` / `settle_parity` 二进制同一套方法）。

> 在离线版里直接填 `http://127.0.0.1:<port>`，或干脆跳过该页直接导航。

## 5. 与联网版的关系

- **同一个前端页面**，零改动 —— 视觉与规则不会分叉（这是当初"不做离线版"的核心理由）。
- **两个 APK 两个包名**，可同时安装：
  - 联网版：`com.zhuoji.mahjong`（当前 v1.1.0）
  - 离线版建议：`com.zhuoji.mahjong.offline`，应用名 **「独山麻将·单机」**
- 离线版**不含**：对局历史云同步、冠军模型动态注册（模型烘焙进包）、局域网多人。

## 6. 建议的取舍（要你拍板）

1. **先做 E-SLIM 再打包离线版**：如果学生瘦身能把 9.85M 压到 1M 且非劣，
   离线包里 `champ` 的搜索档才可能可用；否则离线 v1 只带 **master + P48 贪心**。
2. **离线 v1 是否接受「无搜索档」**：贪心档在手机上就是 0.1–0.4 s/步，体验最好；
   搜索档在手机上是数十秒级，建议先不做。
3. **是否要「讲解」**（`reason.py`）：这是唯一需要额外移植 395 行的部分，可以二期。

> 本轮**没有**开始移植。若你确认继续，我按 O0→O4 推进，每阶段交付可验证的中间产物，
> 不做"看起来能跑"的半成品。

## 7. 实施成本剖析与落地决策（2026-11-11，用户批准「按计划打包」后）

用户 2026-11-11 12:49 明确：**打包离线版**，并把 v1.1.0 的四项 Android 行为
（沉浸全屏隐藏状态栏、5 分钟无操作后允许息屏、幺鸡 logo、横屏可开小窗）一并带过去。
模型按 E-SLIM 收口后的建议：`champ_slim_s`（3.1 MB / enc3 / 0.816M）贪心主力 +
`dushan_master`（2.9 MB / enc1 / 0.769M）后备，**不带 P48**（39 MB，设备端搜索档数十秒级）。
这与 11-10 原话「仅保留 master 和 p48」不同，是 E-SLIM 结果出来后的策略更新。

### 7.1 成本构成（按「必须新写」拆，而非按文件行数）

| 环节 | 现状 | 新增成本 |
|---|---|---|
| 规则状态机 / 结算 / 三版编码 / PIMC 搜索 | `rust_engine` 约 4880 行（70%），纯 Rust、平台无关、已与 Python 逐位对拍 | **0**（直接 path 依赖） |
| `/api/state` 32 顶层字段 + `result` 明细 + `events` | `Game` 无 `Serialize`、无 JSON 视图 | 需新写 `view.rs`（O0，最贵） |
| 会话循环 / 三家 AI 调度 / 连庄 / 累计分 | `Game` 只覆盖单局，`dealer_streak` 从未更新 | 需新写 `session.rs`（O1） |
| 推理后端 | `infer.rs` 是 ORT + CoreML（macOS 专属） | 换成 `tract`（O2） |
| HTTP 服务 + 静态资源同源托管 | 无 | 需新写（O3） |
| Android 工程 / 包名 / 图标 / 四项行为 | v1.1.0 壳已具备 | **复制改造**，非重写 |

合计仍与 §4 的 3.5–4.5 人天一致；**无法靠堆人力压缩的部分是 JSON 视图的逐字段对拍**。

### 7.2 用 Rust 把成本压到最低的五条决策（开工前锁定）

1. **不引入 axum / tokio / hyper**：16 个接口全是短 JSON 请求，前端 450 ms 轮询，
   用 `std::net::TcpListener` 手写 HTTP/1.1（GET/POST + `Content-Length`）即可。
   省掉 30+ 传递依赖、Android 交叉编译时间与包体，也避开异步运行时在
   Tauri Android 进程里的生命周期问题。现有 `lib.rs` 的连通性探测已经证明
   「纯 std 网络」在这条构建链上可用。
2. **不用 JNI AssetManager、不捆 `libonnxruntime.so`**：静态资源
   （`web/static` 10 MB / 242 文件）与两个 ONNX（6.0 MB）用 `include_dir` /
   `include_bytes!` 在**编译期嵌进 .so**，纯 Rust 零平台胶水；`tract` 从内存读模型。
   APK 内不再需要起本地文件服务，也不用担心 assets 路径在 Android 上不可 `File::open`。
3. **tract 0.23.9 全套已在本机 cargo 缓存**（`~/.cargo/registry/cache`），零下载成本。
   若算子不支持再退 ORT Android AAR（+17.6 MB + JNI），但那是失败路径。
4. **复制 v1.1.0 的 Android 壳**（`MainActivity.kt` / Manifest / 幺鸡图标 / keystore /
   gradle 定制）而非 `tauri android init` 重写，四项行为原样继承，只改包名与入口。
5. **按 §5 的允许范围裁剪**：`/api/history*` `/api/replay` `/api/stats` 返回带 `ok`
   的合法空 JSON；`/api/quit` 不实现（前端零调用）；`hint` 优先接真模型，
   tract 不可用时降级 `teacher:balanced` 纯规则启发式（保证 `src_ok=true`）。

### 7.3 验证顺序（先便宜、后昂贵，任何一步失败就地改架构）

1. **tract 算子 spike**（macOS，秒级）：加载 `champ_slim_s.onnx` / `dushan_master.onnx`，
   打印输入/输出 fact，全零前向，再与 Python ORT 逐位对拍。决定整个推理架构。
2. **O0 状态 JSON 对拍**：Rust `view.rs` 输出 vs Python 服务端同 seed 同动作串的
   `/api/state`，逐字段 diff = 0 才准进 O1。
3. **Android 交叉编译 smoke**：只 `cargo build --target aarch64-linux-android --lib`，
   不带 Gradle，先证依赖树能编过。
4. **O1 → O3 → O4**：macOS :8771 打通一手 → 打包 APK → 断网模拟器验收。

### 7.4 已核实的环境事实

- crates.io 可达（HTTP 200 / 0.73 s）；`tract-{core,data,hir,linalg,onnx,opl} 0.23.9`

- Rust targets 含 `aarch64-linux-android`；Android SDK（platform 36 / build-tools /

## 10. 规则引擎对齐与推荐形态（2026-11-11 晚）

### 10.1 根因：离线把前端 `rules` 整份丢了

线上 `web/dushan_server.py` 有 `config_from_rules()`，把设置面板的整套规则
映射进 `DushanConfig`：翻鸡策略、满堂鸡、追加鸡牌种、`scores` 分值表
（含 `jicf` 冲锋鸡）、五项未听包赔开关。离线 `Session::new` 一直写死
`Config::default()`，**这份载荷从头到尾没有被读取**。

后果不是「分数差一点」，而是判定范围直接不同：

- 追加鸡（如八筒）在离线**根本不算鸡** → 不会记冲锋鸡、不会开横鸡轮、
  手牌里也不算鸡分；
- 设置里把冲锋鸡改成 5 分，离线仍按 3 分结算；
- 开局翻鸡在离线永远关闭（`kaiju_fanji=0`），翻出来的种不参与任何鸡判定。

用户看到的「冲锋鸡处理和线上不同步」，就是这条链路断在服务端入口。

修法：新增 `offline/src/rules_cfg.rs::config_from_rules`，与 Python 版本
**逐字段对应**（键名、默认值、`_f` 的非负回落、翻鸡的中文/bool 别名、
追加鸡的越界/去重清洗都照抄）。`Session` 保留一份 `cfg`，`/api/new` 与
`/api/next` 都解析 `rules`，后者用于「下一局生效」的设置项。
`Config` 新增 `extra_ji: u32` 掩码，在 `new_with_wall` 发牌后并入
`ji_tiles = 幺鸡 ∪ extra_ji`，与 `DushanGame._init_dushan_state` 同序。

### 10.2 冲锋鸡到底怎么算（现行线上口径）

仓库里有两套历史实现，容易读串：

| 文件 | 是否线上在用 | 冲锋鸡口径 |
|---|---|---|
| `zhuoji/rules.py` | 否（旧基类，只被 `DushanGame` 继承动作/阶段常量） | **全局第一张幺鸡**：`_first_yaoji_discarded` + `chongfeng_player` 单值 |
| `zhuoji/dushan.py` | **是**（线上 `DushanGame`） | **每家自己打出的第一张鸡牌**（每家最多一次，最多 4 只）；追加种与开局翻鸡种同权 |
| `rust_engine/src/state.rs` | 离线/训练共用 | 与 `dushan.py` 一致：`!first_discard_done[p] && ji_tiles & bit(tile)` |

横鸡的定义（三处必须同源）：该鸡牌种**全场第一张非冲锋鸡**开轮，轮内其他家
跟打同种鸡都算横鸡；开轮者或轮内已打过的人**再次出牌**时该轮收口，收口后
同种鸡按普通鸡计。

### 10.3 修掉的两处内核偏差

1. **`ji_name_if_discarded` 多判了 `joined`**
   旧代码：轮已开、但自己已在轮内 → 返回普通鸡。`dushan.py` 只看
   `_hengji_rounds.get(tile)` 是否还开着，是就返回横鸡。这不仅是 UI 预览
   不一致 —— `encode_v3` 的 `ji_name` 特征也调这个函数，离线推理与训练时的
   特征分布会分叉。已删除 `joined` 条件。

2. **「碰幺鸡 → 冲锋鸡转责任鸡」是不可达死代码**
   该分支依赖 `chongfeng_player`，而它在状态推进中从未被赋值（只有旧快照
   导入才给值），条件恒不成立；且 `dushan.py` 的新引擎早已没有「责任鸡」，
   被碰走的鸡由 `claimed_ji` 表达（分数归碰者、打出者付溢价）。删掉，避免
   将来导入旧快照后与线上行为分叉。

### 10.4 推荐形态：离线只给概率，不给理由

离线的四档都是**单模型贪心**（一次前向取 argmax），没有搜索树，也就没有
「进张对比 / 期望差 / 风险」这类可解释项。因此：

- 「推荐理由」下拉里**不提供「一句话推荐」**（存量配置 `brief` 自动回落
  `full`），只留「完整推荐 / 仅推荐出牌」；
- 完整面板只渲染 `序号 + 动作 + 概率 + 条形`，不渲染 `tags / lines / reason`，
  也不显示 💡 一句话；面板标题从「大师建议 · 牌技讲解」改为「建议 · 仅概率」；
- 局面速览（向听/持鸡/报叫）保留 —— 那是状态读数，不是模型解释。

判定开关是 `IS_OFFLINE = !!window.__DUSHAN_TIERS`：注入只有离线宿主会做，
联网版不注入，行为零分叉（已双向回归）。

### 10.5 验收

- 对拍：`tools/settle_parity.py` 304 局（含 8 个定向），随机局里加入
  `extra_ji`（0/1/2 个种）与自定义 `jicf`（1.5/3/5），`mismatch=0`；
- 内核单测：`extra_ji` 并入 `ji_tiles` 且首张即冲锋鸡；横鸡轮内参与者
  再打同种仍记横鸡、收口后转普通鸡；
- 离线服务实测：默认 `ji_tiles=[9]`；传 `extra_ji=[7]` + `kaiju=both`
  后 `ji_tiles=[7,9,20,22]`；
- 面板实测（headless）：离线 3 个候选全部 `hasReason=false`、无 💡；
  联网版仍有 `hint-reason` 与提示语。

## 11. 双模式启动页与两处 UI 修正（2026-11-12）

### 11.1 启动页：在线 / 离线 二选一

`tauri-offline/src/index.html` 从「开机即自动进离线」改成显式的模式选择页：

| 模式 | 行为 |
|---|---|
| 在线模式 | 填局域网服务端地址（可改、记住、测试连接）→ `enter_online` 导航到移动网页版，自动补 `?touch=1`，资源完全由服务端提供 |
| 离线模式 | 等 `127.0.0.1:8791` 的本地 Rust 引擎就绪 → `enter_game`，断网可玩 |

本地引擎仍在后台线程提前加载（选模式前就开始），所以切到离线模式通常无需等待；
**但绝不自动导航**，用户没选就不进任何模式。浏览器预览下在线直接跳转、离线只给提示。

### 11.2 对手出牌节奏：手填秒数不生效的根因

离线 `Session::new` 固定 `speed=0.45` 且 `/api/new` 完全忽略请求里的 `speed`；
`snapshot()` 又把 speed 当作「每次轮询推进几步」的分桶（≥2 秒反而一次走 3 步），
方向还是反的。现在：

- `/api/new` 把 speed 落到会话；`/api/speed` 立即重算放行时刻（不必等旧节奏走完）；
- `snapshot()` 用单调时钟记录 `next_ai_at`，每两个 AI 动作至少隔 speed 秒，
  `speed=0` 一次推到我的决策点（瞬发）；自己出完牌也重新计时，与线上
  `time.sleep(self.speed)` 同口径；
- 实测（本机离线服务，轮询 80 ms）：`2.0s → 2.03/2.01/2.09s`、
  `0.5s → 0.52/0.53/0.52s`，局中 `3s→0.5s` 立刻切到 `0.52s`；
- 前端四个常用档改为 **0.5 / 1 / 2 / 3 秒**（设置面板与开局页同源），
  手填值保留两位小数（不再被 0.1 秒取整吞掉），一次性迁移旧四档
  `0/0.2/0.45/0.8`；两处输入框在任一处改动后同步，避免开局页旧值回写。

### 11.3 结算翻鸡牌漏标红点

`res.fanji_tiles` 只在「结算信息条」有回推（缺省时按指示牌 + 模式算），
手牌/弃牌/副露却各算一份 `st.ji_tiles`；字段缺失或翻鸡种未进 `ji_tiles`
时就会出现「信息条四六条、手里只有六条带点」。现在统一为：

- `fanjiTilesOf(res)`：全 UI 唯一的翻鸡牌种真源（显式字段优先，缺省按
  `fanji_flip + jiesuan_fanji` 回推，与 Rust `fanji_mask` 同源）；
- `activeJiSet(st)`：本局鸡种 ∪ 结算翻鸡种，桌面手牌 / 弃牌 / 副露 /
  结算总览全部调用它；`meldHTML` / `ovMeldCaption` 增加可选 `st` 参数，
  回放帧与结算帧不再误用上一局状态（**2026-11-12 实机反馈后已收窄：
  翻鸡种只对手牌有效，见 §12.3**）；
- 新一局开始时清空 `RES_SRC`，防止上一局翻鸡种给下一局手牌点红点。

### 11.4 档位文案

## 12. 展示机制与鸡牌口径再统一（2026-11-12 实机反馈）

联网版与离线版共用**同一份** `web/static/dushan.html`，但前端能画出什么
取决于服务端下发的 state。实机发现离线 `view.rs` / `session.rs` 里有三处
占位空值，导致共用页面在单机版「缺半个身子」。

### 12.1 碰牌后弃牌墙原位灰显残牌

- 线上 `DushanGame` 有 `discard_view` / `discard_claimed_view` 两张
  **只增不减的展示视图**：碰/明杠时只把对应位标 `true`，牌仍留在牌河，
  前端 `.mc.claimed` 渲染成半透明 + 虚线描边。
- Rust `Game` 原先只有逻辑 `discards`，碰/杠直接 `pop()`；`view.rs` 又硬编码
  `discard_claimed = vec![false; n]`。结果离线版被碰的牌凭空消失。
- 修复：`state.rs` 加 `discard_view` / `discard_claimed_view`，`step_discard`
  同步 push，碰/明杠只改展示位；`view.rs::snapshot` 的 `players[].discards`
  改用展示视图，`discard_claimed` 下发真值。**记牌器 counter 仍走逻辑
  `discards`**（被吃走的牌由副露补 3/4 张），与线上 `_snapshot` 一致。

### 12.2 冲锋鸡 / 横鸡的动画、角标与结算标签

| 字段 | 原来 | 现在 | 前端用途 |
|---|---|---|---|
| `events[].ctag` | 恒 `""` | step 后读 `ji_tag_of_last` 映射中文 | 全屏特效 `jiFx` / toast |
| `players[].discard_tags` | 恒 `null` | `view::discard_tags(g,p)` 按 `ji_events` 顺序对回**展示视图** | 牌河 3/2/1 点标、结算「打出鸡牌」标签 |
| `melds[].ji` | 恒 `null` | `view::meld_ji_tag(g,p,t)` 从 `claimed_ji` 取类型 | 副露「碰横鸡(某某)」与冲/横角标 |

- `ji_tag_cn()` 把引擎 `JI_CHONGFENG/JI_HENG/JI_PLAIN` 映射成
  「冲锋鸡/横鸡/幺鸡」，与 `dushan.py` 的字符串同源。
- `ctag` **必须 step 之后回填**：`ji_name_if_discarded()` 在「该种第一次开
  横鸡轮」时会预测成普通鸡，与 `step_discard` 实际记下的横鸡不一致。
- 顺带补 `hengji` 事件（按 `hengji_open` 掩码变化推 open/close），离线版
  流水也有「开出横鸡轮 · X / 横鸡轮结束」。

### 13.1 结算翻鸡：副露里的牌也要打点（改口，见 13.2 的口径边界）

### 14.6 安卓返回键：在线模式也回选择页（2026-11-12 追加反馈）

**现象**：模式选择页进「在线模式」→ 进网页版后按返回键直接退出 App；离线模式正常。

**根因有三层**（第三次才挖到底）：

1. `MainActivity` 缓存了 `onWebViewCreate` 给的 WebView 引用。Tauri 导航到局域网地址后
   这个实例可能已从视图树 detach，`wv.url` 读到空串 → 被 `url.isEmpty()` 判成
   「已在选择页」→ 走 `finish()`。现在每次返回都用 `currentWebView()` 在
   `window.decorView` 里现找（取最后一个 WebView），找不到才退回缓存引用。
2. 选择页与两个面板是**同一个 URL 的 SPA**，没有历史记录，`goBack()` 无从下手。
   现在 `main.js::show(id)` 把面板状态写进 **URL hash**（`#online-pane` / `#offline-pane`），
   原生层只读 `wv.url` 就能判断当前在哪一屏，不需要 Kotlin 猜状态。
3. **Wry 自带的返回回调把我们的压在下面**（决定性的一条）。
   `WryActivity.handleBackNavigation` 是 `open val`（默认 `true`），Wry 在
   `setWebView()` 里据此注册自己的 `OnBackPressedCallback`。而 `setWebView()`
   发生在 `onCreate` **之后**，于是 Wry 的回调后注册、占据 dispatcher 栈顶，
   我们在 `onCreate` 里注册的回调**一次都不会被调用**——`logcat` 里连一行日志都没有
   就是这个信号。表现：面板页按返回能回选择页（Wry 的 `webView.goBack()` 干的），
   选择页没有历史时 `goBack()` 落空又不 `finish`，于是「按了没反应」。
   修法是在子类覆盖：

   ```kotlin
   override val handleBackNavigation: Boolean = false
   ```

**排查信号**：先 `Log.w` 一行在回调里，`adb logcat -s DushanBack` 看有没有输出。
没输出就别再调业务逻辑了，是回调根本没进门；有输出才去看 URL / 分支。

**当前口径**（2026-11-12 晚三次实机复核后定稿）：

| 当前 URL | 返回键行为 |
|---|---|
| `http://tauri.localhost/`（选择页根，无 hash） | 退出 App |
| `http://tauri.localhost/#online-pane` / `#offline-pane` | `loadUrl(选择页)` + `clearHistory()` |
| 游戏页 `http://127.0.0.1:8791/?touch=1` | `loadUrl(选择页)` + `clearHistory()` |
| 在线网页版（任意局域网地址） | `loadUrl(选择页)` + `clearHistory()` |

外链不用 `goBack`：历史里是「选择页 → 在线面板 → 外链」，后退只会退到在线面板，
用户要按两次。直接 `loadUrl` 一步到位。

**判据为什么是 URL hash 而不是 JS 回调**：安卓返回键是**原生同步事件**，
而 `evaluateJavascript` 是异步的。若页面刚好在重载（`loadUrl` 尚未完成、
`main.js` 还没执行），回调可能整段丢失 —— 实测表现就是**选择页按第一次返回
没反应、按第二次才退出**。现在面板状态同步写进地址：

```js
// main.js::show(id)
var base = location.href.split("#")[0];
var next = (id === "chooser") ? base : base + "#" + id;
try { history.replaceState({ pane: id }, "", next); } catch (e) {}
```

Kotlin 侧只看 `wv.url`，零异步、零猜测：

```kotlin
val url = wv.url.orEmpty()
val onChooser = url.startsWith(CHOOSER_URL) || url.startsWith("about:blank")
if (onChooser && !url.contains("#")) { exitApp(); return }
wv.loadUrl(CHOOSER_URL); wv.clearHistory()
```

一律 `replaceState`（不再 `pushState`）：历史里始终只有一条记录，
不存在「loadUrl 之后 canGoBack 仍为 true、退回面板」的问题。

**同时移除**：「在线模式 · 移动网页版」面板里的 `‹ 返回` 按钮（用户口径），
离线面板的按钮保留，点击改为直接 `show("chooser")`，与系统返回键同一条路径。

### 14.7 两个「改了没生效」的坑（2026-11-12 实机排查）

**① 启动页页脚版本号永远是 v1.0.0**：`index.html` 里的 footer 只是首帧占位，
`main.js` 在 `IN_APP` 时用 `invoke("app_info")` 的 `version` **覆盖**它。而
`app_info` 原来返回 `env!("CARGO_PKG_VERSION")` —— 那是 `tauri-offline/src-tauri`
这个 crate 的 `Cargo.toml` 版本（1.0.0），与 `tauri.conf.json` / APK 的
`versionName`（1.2.0）是**两套版本号**。已改为 `app.package_info().version`，
并把 crate/package.json 一起升到 1.2.0，从此只有一处真源。

排查时别只盯着 HTML：先确认「谁在写这个 DOM」，`grep -n footer src/main.js`
一眼就能看到覆盖逻辑。

**② 改 `src/*` 后必须确认 `.so` 真被重编**：Tauri 把 `frontendDist` 的内容
brotli 压缩进 `.so`，压缩结果缓存在
`src-tauri/target/<triple>/release/build/tauri-app-*/out/tauri-codegen-assets/`
（内容寻址，文件名是 sha256）。验证「某一版页面到底进没进包」的可靠办法是
拿缓存里的压缩块字节去 `.so` 里 `find()`：

```bash
# 命中即说明该版资源真的编进 .so 了
python3 - <<'PY'
so=open('lib/arm64-v8a/libtauri_app_lib.so','rb').read()
blob=open('.../tauri-codegen-assets/<sha>.html','rb').read()
print(so.find(blob) >= 0)
PY
```

`.so` 里搜不到页面中文是**正常**的（已压缩），别据此判断「没编进去」。

不是数字 —— 早期用 `as_u64()` 读到恒 255，`one_line` 的同类比较整段失效。
前端 `paintCoach()` 的 `showWhy` 也改为按数据自适应（离线只要有 lines/tags/tip 就显示）。

### 15.3 在线模式：局域网自动发现，不再写死地址

用户口径「app 的网页在线版本链接能不能不定死地址，而是在局域网内自动扫描？
自动扫描到服务端然后连接上」。协议（Rust 侧 `tauri-offline/src-tauri/src/lib.rs`
与 Python 侧 `web/dushan_server.py::start_discovery` 逐字节一致）：

| 阶段 | 做法 | 备注 |
|---|---|---|
| ① UDP 广播（首选，≤1.2 s） | 向 `255.255.255.255:{8770,8771}` 发 `DUSHAN?`，服务端回 `DUSHAN1 <port>` | 应答包的**来源 IP** 就是服务端地址，不用自己拼网段；每 200 ms 重发一次抗丢包 |
| ② TCP 扫描（兜底） | 仅在①全空时跑：本机 IP 所在 /24 × 两个端口，48 worker、单连接 220 ms | 部分路由/ROM 会丢受限广播 |
| ③ 校验 | 每个候选都过 `GET /api/meta` 必须 200 | 任何占用 8770 的进程都连得上，只有本服务端能答 `/api/meta` |

服务端一侧：`offline/src/http.rs::serve_on` 在 HTTP 端口上再绑一个 UDP socket
（不同协议栈，不冲突）起应答线程；绑定失败只打一行日志，绝不影响对局。

前端（`tauri-offline/src/index.html` + `main.js`）：进「在线模式」面板即自动扫描
→ 扫到 1 个直接连（`enterOnline` 延时 550 ms 进入）、≥2 个列成候选让用户点选、
0 个才回填「上次成功地址」并提示手填；「扫描」按钮可随时重扫。地址只记
`localStorage.zhuoji_online_server` 作为**上次成功值**，不再是默认连接目标。

### 15.5 听牌计算器的「剩余张数」要扣自己和明牌

用户口径：2345 筒听 2/5 筒，弃牌里没有这两张时应显示**各剩 3 张**（原来恒 4）。
`offline/src/session.rs::ting_payload` 里 `left` 的计算口径改成：
`4 − (四家牌河 + 四家副露(碰 3 / 杠 4) + 我的暗手 − 本次打出的那张)`，封顶 0；
牌河用**逻辑视图**（被碰/杠/胡走的那张已 pop，不算已见）。`cur`（13 张等别人打）
与 `map`（14 张逐张试打）分别按 `drop = None / Some(t)` 计算。

### 15.6 点炮胡走的那张牌：牌河灰显 + 结算页归赢家

用户口径：「玩家 a 打出 2 筒被 b 抓炮，翻鸡出来 2 筒是鸡牌，这张鸡牌 2 筒
应该归属玩家 b。计算逻辑是对的，但 a 的弃牌堆没有半透明，且结算页面仍把
这张 2 筒渲染到 a 的手牌后面（当成 a 手里的鸡牌）」。

- 引擎（`rust_engine/src/settle.rs::settle_win` 与
  `zhuoji/dushan.py::_settle_win_multi`）：点炮/热炮把那张从 `discards` 里 pop 时，
  同步把 `discard_claimed_view` 对应位标 `true`（与碰/明杠吃走同一套展示机制）。
- 前端：牌河 `.mc.claimed` 的 tooltip 改成「已被碰/杠/胡走」；结算页
  `playerHandBlock` 里「打出的鸡牌」行**跳过被胡走的那张**
  （判定：本家是 `res.loser` + 非自摸 + 牌河最后一张等于 `res.win_tile`），
  它已经在赢家手牌里计鸡。实测：同一局面修复前放炮者行里 4 万出现 2 次，
  修复后 1 次（被胡走的那张消失），牌河末张带 `mc claimed`。

### 15.7 责任鸡溢价的方向：随「碰/杠者是否听牌」反转

用户口径（2026-11-12，覆盖 2026-10-08 的旧口径）：「玩家 a 打出鸡牌、玩家 b
碰了这张鸡牌，但结算时 b 没有听牌，那 a 就不用付这个责任鸡，反而是 b 需要
多赔 a 的责任鸡溢价」。

| 碰/杠者终局 | 溢价方向 | AB 之间合计 |
|---|---|---|
| 听牌 | 打出者 → 碰/杠者（原口径） | 碰冲锋 5 / 碰横 4 / 杠冲锋 9 / 杠横 8 |
| 未听牌 | **碰/杠者 → 打出者**（同额） | 仍是 4（3 张面值走包鸡 + 1 溢价反向） |

实现：`ji_claim_detail` 每条多带 `payer / payee`（两个引擎同名字段、同算法，
`payer = 打出者 if 碰者听牌 else 碰者`），结算直接 `pflow(payee, payer, …)`。
原先「未听牌 → 溢价并入包鸡块反向结算」的那段删除 —— 溢价只跟听牌有关，
与包鸡开关无关。全烧者（热炮放炮者 / 被抢杠者）一律**不收**（以 `payee` 判定）。
前端 `zrRows/zrChips/zrPrem` 改按 `payer/payee` 取行（旧归档无该字段时回落到
「碰者收」的老方向）。
