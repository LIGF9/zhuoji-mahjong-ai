# 离线版可行性与实施方案（2026-11-10，v2 修订）

> **结论先说**：离线版**技术上可行**，但不是「重新打个包」——它要求把 Python 服务端
> 的编排层（`web/dushan_server.py` 3286 行，其中 `Session` **1528 行 / 42 个方法**）
> 在 Rust 里重建，并在设备上跑推理。本轮**未**交付可用的离线 APK；本文给出
> 实测数据、缺口清单、分阶段方案与验收口径，供你决定是否继续投入。
>
> 同轮已交付：联网版 APK v1.1.0（沉浸全屏 / 5 分钟亮屏 / 幺鸡图标 / 允许小窗）。
>
> **v2 修订（同日，读代码后）**有三处判断变化，工作量比 v1 估算**下降约一半**：
> 1. Rust 的 `Game` 是**完整**状态机（`new_with_wall` 可从洗好的牌墙开局，
>    `legal_actions`/`step` 覆盖摸打碰杠胡全流程，**且独山麻将无定缺阶段**），
>    所以"移植 1528 行编排"实际是"写会话循环 + JSON 视图"，不是逐行翻译；
> 2. 前端可以**一字不改**——在 APK 内起一个 127.0.0.1 的本地 HTTP 服务，
>    把同一份 `dushan.html` 与同名 `/api/*` 路由原样提供出去，WebView 指向它即可；
> 3. 推理后端**不必**捆 ONNX Runtime（见 §3.2），纯 Rust 的 `tract` 能省掉 17.6 MB
>    的 `libonnxruntime.so` 与 JNI 打包风险。

---

## 1. 为什么「把网页打进去」不够

现有客户端（`tauri-app/`）是**局域网直连**：Rust 侧只做「记地址 / 探连通 / 导航」，
游戏页面、规则、AI 全在你电脑的服务端。离线的本质是**把那台电脑搬进手机**。

| 层 | 现状 | 离线需要 |
|---|---|---|
| 前端页面 | `web/static/dushan.html` 582 KB，零依赖 | 直接复用（**不用改**） |
| HTTP 接口 | 16 个 `/api/*`，`/api/state` 单次 32 个顶层字段 | Rust 里实现同构接口 |
| 对局编排 | Python `Session` 1528 行 / 42 方法（轮转、碰杠胡响应窗口、鸡账、报叫、抢杠、同轮跟打、结算入账） | 在 Rust 写会话循环（状态机已有，见下） |
| 规则/结算 | Python `zhuoji/dushan.py` 1607 + `rules.py` 711 | **Rust 已有**：`state.rs` 1005 + `settle.rs` 1140（已与 Python 逐位对拍） |
| 搜索 | `rust_engine/src/{search,deep}.rs` | **Rust 已有**（热路径）。网络前向由 `take_batch()/feed()` 协议外挂，后端可换 |
| 网络推理 | PyTorch / ORT（macOS CoreML） | 纯 Rust `tract`（首选）或 Android ORT |
| 讲解/听牌 | `zhuoji/reason.py` 395、`ting_*` | 需移植或降级 |

**已有资产比想象中多**：规则、结算、编码（v1/v2/v3）、搜索骨架、determinization 全在 Rust，
`annotate` 二进制已经用 ORT 跑前向（`rust_engine/src/infer.rs`，`ch/gdim` 可配 15/70 与 63/130）。
更关键的两点：

- `Game::new_with_wall(wall, dealer, cfg, ft)` 支持**从任意洗好的牌墙开局**，
  `legal_actions(t)` + `step(a, t)` 覆盖摸打碰杠胡全流程，`Outcome` 走 `settle.rs`。
  **独山麻将没有定缺阶段**（`grep 定缺 zhuoji/dushan.py` 无命中，`state.rs` 的
  `phase` 只有 `DISCARD/SELF_KONG/RESPOND/OVER`），所以开局后不存在"等玩家选缺门"这类状态，
  会话循环比预想的短。
- `Search` 的网络是**外挂批协议**：`needs_net()` → `take_batch()` → 外部算 → `feed(actions, values)`。
  这意味着设备端只需要实现「一批编码张量 → 一批 Q」，搜索档与贪心档**共用同一段代码**。
**缺的是「会话循环 + JSON 视图 + 设备打包」**，不是「从头写一个麻将」。

## 2. 实测数据（本机 + 官方包，非估算）

| 项 | 数值 | 来源 |
|---|---|---|
| `onnxruntime-android` arm64 `libonnxruntime.so` | **17.6 MB** | Maven 1.20.0 AAR 实测 |
| `champ_exit_p48.onnx` | 39 MB | `models/onnx/`，9.850M 参数（160ch×20，enc v3） |
| `dushan_master.onnx` | 2 MB | 同上，**0.769M 参数（64ch×8）**——与 E-SLIM 目标同量级 |
| 预估离线 APK（单 ABI，`tract` 版，**master + slim_s**） | **≈ 13–16 MB** | 7.2 MB（现包）+ 2 + 3.1（推荐方案） |
| 预估离线 APK（同上，若再加 P48） | ≈ 50–54 MB | 再加 37.5（P48 搜索在手机上不可用，见 §3.1） |
| 预估离线 APK（同上，若捆 ORT 再加） | +17.6 MB | 不推荐，见 §3.2 |
| `/api/state` 顶层字段 | 32 个（含 `players[4]` / `pending` / `stats` / `events`） | 抓取真实响应 |
| 前端调用接口数 | 16 个 | 静态扫描 `dushan.html` |
| Python 编排层 | 1528 行 / 42 方法 | `class Session` 行数统计（含历史/统计/回放 I/O） |

## 3. 三个必须先解决的技术风险

1. **设备端推理速度未知（最大风险）**
   手机是 CPU/NNAPI，不是 ANE。同机（M 系列，空载，v3 编码）实测：

   | 模型 | 参数 | 贪心单步 | N32 单步 | ONNX |
   |---|---|---|---|---|
   | `dushan_master`（v1 编码） | 0.769M | 0.66 ms | — | 2 MB |
   | `champ_exit_p48` | 9.8367M | 4.5083 ms | **1.8111 s** | 37.5 MB |
   | `slim_s`（E-SLIM 学生） | **0.8141M** | **0.9211 ms** | **0.2749 s** | **3.1 MB** |

   手机大核通常比本机慢 2–4×。⇒ **贪心档全程可实时**；P48 的 N32 在手机上会是
   **5–10 s/步**，一盘几十步 = 数分钟，**不可用**；而 `slim_s` 的 N32 上手机约
   **0.6–1.1 s/步**，是**唯一在手机上可能可用的搜索档**。

   **建议据此调整模型清单**：原需求「只保留 master 和 P48」在离线场景下不划算——
   P48 独占 37.5 MB 体积、且它的搜索在手机上跑不动，只能当"思考档/讲解"；
   而 `slim_s` 3.1 MB 就能提供可用搜索。**推荐包内带 `master` + `slim_s`（模型共约 5 MB），
   P48 不带**；若坚持要 P48，包体 +37.5 MB，且它的搜索档只能标注"等 5–10 秒/步"。

   **定稿（2026-11-10 19:0x，用户口径「slim_s 给 web 并给离线版」）**：
   `slim_s` 已作为 `champ_slim_s` 注册进线上（`models/champions.json`，只增不替），
   并导出按 stem 隔离的 `models/onnx/champ_slim_s.onnx`（3.3 MB，enc 3 / 63-130，四头齐，
   `tools/export_onnx_cache.py` 四项校验 PASS）。离线包直接复用同一份权重与 ONNX，
   **不另存一套文件**，避免线上/离线数值分叉。统计依据见
   `reports/E-SLIM-学生瘦身.md`（闸门 A 非劣 p=1.35e-05；字面 TOST 双侧因"显著更好"
   不成立，已登记为预登记措辞缺陷）；独立池复现与 vs P48 直接对打见
   `runs/gates/slimB_*`。

   **主力选谁：用 `slim_s`，`master` 降为后备（2026-11-10 23:3x，据追测矩阵更新）**

   同池（`7_400_000`）四臂实测把这件事钉死了：

   | 谁是 AI，对手都是 master+N32 | 分差 |
   |---|---|
   | `slim_s`（0.82M，贪心） | **+0.855 ± 0.266**（600 seed） |
   | `champ_exit_p48`（9.84M，贪心） | +1.946 ± 0.402（300 seed） |

   ⇒ 学生**只走贪心就胜过开了搜索的 master**，且它贪心单步 0.9211 ms（`master` 0.66 ms 同量级）、
   N32 0.2749 s。因此离线版对局 AI 的推荐顺序是：

   1. **主力 = `champ_slim_s` 贪心**（默认档，手机上实时）；
   2. **搜索档 = `champ_slim_s` N32**（约 0.6–1.1 s/步，桌面节奏可接受）；
   3. **`master` 只作后备/回退**（2 MB，v1 编码 15 通道，与学生的 v3 两套张量，
      同时带会让 `annotate` 侧要两套编码分支——若包体紧张，**可以只带学生**）。

   附带一条量化事实：`master` 打开 N32 搜索 ≈ 白拿 **3.0 分**（同池配对差
   +2.997±0.551）。这说明手机上若跑不动 P48 的搜索，用学生的 N32 才是把"搜索红利"
   搬到设备的唯一现实路径。

2. **推理后端选型：`tract` 优先，ORT 兜底**
   - `tract-onnx` 是纯 Rust、无动态库、交叉编译到 `aarch64-linux-android` 干净（不碰 JNI/`loadLibrary`），
     编译后约 +2–4 MB，**能省掉 17.6 MB 的 `libonnxruntime.so`**；
   - 代价是数值与算子覆盖需要验证：本仓库的网只用到 conv/bn/relu/add/linear/softmax/SE 池化/dueling 拼接，
     属于 tract 的成熟算子，风险低但**必须过 §3.3 的逐位对拍**；
   - 若 tract 在某个算子上失败或慢于阈值，退回 `ort` + Android AAR（已验证 Maven 可下载、ABI 齐全，
     属**确定性工作**，非未知）。
3. **JSON 契约必须逐字段一致**：前端对 `phase/pending/players/events` 的字段名与语义敏感。
   对策：拿现网服务端做**黄金样本**——同一 seed、同一串动作，两边回放后逐字段 diff，
   差异为 0 才算通过（与 `rust_engine` 已有的 `parity` / `settle_parity` 二进制同一套方法）。

## 4. 分阶段方案（每阶段都可独立验收）

| 阶段 | 内容 | 产出 | 估算 |
|---|---|---|---|
| **O0** | `Game → /api/state` JSON 视图 + `/api/meta`；`parity` 扩展为「状态 JSON 逐字段对拍」 | `cargo run --bin parity -- --state-json` 与 Python 零差异 | 0.5–1 天 |
| **O1** | 会话循环：`new / act / next / end_hand / hold / speed`，三家 AI = 贪心（master），结算走 `settle.rs` | 本机 macOS 上 `:8771` 可离线打完一手 | 0.5–1 天 |
| **O2** | `tract` 推理后端接 `take_batch/feed`；`/api/hint`、`/api/ting`、`/api/stats`、`/api/history*`（本地文件） | 功能对齐联网版（hint 可选 N32） | 1 天 |
| **O3** | 打包：模型进 `assets`，APK 内起 axum 本地服务（127.0.0.1 随机端口）**原样托管 dushan.html**，WebView 指向它 | **离线 APK**、断网可玩、前端零改动 | 1 天 |
| **O4** | 设备实测调优：线程数、模型选择、首帧加载、耗电 | 真机帧率/耗时表 | 0.5 天 |

合计 **3.5–4.5 个工作日**（单机、不并发；v1 估 4–5.5，因上面三处修订而下调）。

> O3 的关键技巧：**不改前端一行**。`dushan.html` 现在按"当前 origin"发 `/api/*` 相对请求，
> 在 APK 内起同源本地服务后，它自己就会打到 Rust 端；`tauri-app` 现有的"输地址"入口
> 在离线版里直接填 `http://127.0.0.1:<port>`，或干脆跳过该页直接导航。

## 5. 与联网版的关系

- **同一个前端页面**，零改动 —— 视觉与规则不会分叉（这是当初"不做离线版"的核心理由）。
- **两个 APK 两个包名**，可同时安装：
  - 联网版：`com.zhuoji.mahjong`（当前 v1.1.0）
  - 离线版建议：`com.zhuoji.mahjong.offline`，应用名 **「独山麻将·单机」**
- 离线版**不含**：对局历史云同步、冠军模型动态注册（模型烘焙进包）、局域网多人。

## 6. 建议的取舍（要你拍板）

1. **先做 E-SLIM 再打包离线版**：如果学生瘦身能把 9.85M 压到 1M 且非劣，
   离线包里 `champ` 的搜索档才可能可用；否则离线 v1 只带 **master + P48 贪心**。
2. **离线 v1 是否接受「无搜索档」**：贪心档在手机上就是 0.1–0.4 s/步，体验最好；
   搜索档在手机上是数十秒级，建议先不做。
3. **是否要「讲解」**（`reason.py`）：这是唯一需要额外移植 395 行的部分，可以二期。

> 本轮**没有**开始移植。若你确认继续，我按 O0→O4 推进，每阶段交付可验证的中间产物，
> 不做"看起来能跑"的半成品。
