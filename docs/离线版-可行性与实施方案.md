# 离线版可行性与实施方案（2026-11-10）

> **结论先说**：离线版**技术上可行**，但不是「重新打个包」——它要求把 Python 服务端
> （`web/dushan_server.py` 3286 行，其中 `Session` 编排层 **1528 行 / 42 个方法**）
> 移植到 Rust，并在设备上跑 ONNX 推理。本轮**未**交付可用的离线 APK；本文给出
> 实测数据、缺口清单、分阶段方案与验收口径，供你决定是否继续投入。
>
> 同轮已交付：联网版 APK v1.1.0（沉浸全屏 / 5 分钟亮屏 / 幺鸡图标 / 允许小窗）。

## 1. 为什么「把网页打进去」不够

现有客户端（`tauri-app/`）是**局域网直连**：Rust 侧只做「记地址 / 探连通 / 导航」，
游戏页面、规则、AI 全在你电脑的服务端。离线的本质是**把那台电脑搬进手机**。

| 层 | 现状 | 离线需要 |
|---|---|---|
| 前端页面 | `web/static/dushan.html` 582 KB，零依赖 | 直接复用（**不用改**） |
| HTTP 接口 | 16 个 `/api/*`，`/api/state` 单次 32 个顶层字段 | Rust 里实现同构接口 |
| 对局编排 | Python `Session` 1528 行 / 42 方法（轮转、碰杠胡响应窗口、鸡账、报叫、抢杠、同轮跟打、结算入账） | 移植到 Rust |
| 规则/结算 | Python `zhuoji/dushan.py` 1607 + `rules.py` 711 | **Rust 已有**：`state.rs` 1005 + `settle.rs` 1140（已与 Python 逐位对拍） |
| 搜索 | `rust_engine/src/{search,deep}.rs` | **Rust 已有**（热路径）。但网络前向在 Python 侧 |
| 网络推理 | PyTorch / ORT（macOS CoreML） | Android ORT（arm64）+ 模型文件 |
| 讲解/听牌 | `zhuoji/reason.py` 395、`ting_*` | 需移植或降级 |

**已有资产比想象中多**：规则、结算、编码（v1/v2/v3）、搜索骨架、determinization 全在 Rust，
`annotate` 二进制已经用 ORT 跑前向（`rust_engine/src/infer.rs`，`ch/gdim` 可配 15/70 与 63/130）。
**缺的是「会话层 + JSON 视图 + 设备打包」**，不是「从头写一个麻将」。

## 3. 三个必须先解决的技术风险

1. **设备端推理速度未知（最大风险）**
   手机是 CPU/NNAPI，不是 ANE。参考本机 CPU 上 master 单状态前向约 60–100 µs、
   P48（9.85M）约 600–900 µs；手机大核通常慢 2–4×。
   ⇒ **贪心档可实时**（master 一步 ≈ 0.1–0.4 s）；**N32 搜索（约 1 万状态/决策）在手机上会是
   数十秒级，不可用**。所以离线 v1 必须**只做贪心档**，搜索档要么不做，要么标注「等 10–40 秒」。
   这也正是 E-SLIM 学生瘦身（§6.73）对离线版价值最大的地方。
2. **ORT 动态库打包**：`ort` crate 用的是 `load-dynamic`，需要在 `System.loadLibrary` 之前把
   `libonnxruntime.so` 放到位并设 `ORT_DYLIB_PATH`；Tauri 的 gradle 侧要额外 `jniLibs`。
   已验证 Maven 可下载、ABI 齐全，属于**确定性工作，不是未知**。
3. **JSON 契约必须逐字段一致**：前端对 `phase/pending/players/events` 的字段名与语义敏感。
   对策：拿现网服务端做**黄金样本**——同一 seed、同一串动作，两边回放后逐字段 diff，
   差异为 0 才算通过（与 `rust_engine` 已有的 `parity` / `settle_parity` 二进制同一套方法）。

## 4. 分阶段方案（每阶段都可独立验收）

| 阶段 | 内容 | 产出 | 估算 |
|---|---|---|---|
| **O0** | Rust 侧 `Game → /api/state` JSON 视图 + `/api/meta`；`parity` 扩展为「状态 JSON 逐字段对拍」 | `cargo run --bin parity -- --state-json` 与 Python 零差异 | 0.5–1 天 |
| **O1** | 会话层：`new / act / next / end_hand / hold / speed`，三家 AI = 贪心（master），结算走 `settle.rs` | 本机 macOS 上 `:8771` 可离线打完一手 | 1–1.5 天 |
| **O2** | 补齐 `/api/hint`（贪心 + 可选 N32）、`/api/ting`、`/api/stats`、`/api/history*`（本地文件） | 功能对齐联网版（搜索档可选） | 1 天 |
| **O3** | Android 打包：ORT `.so` + 两模型进 assets，Tauri 侧起本地 HTTP（127.0.0.1 随机端口），WebView 指向它 | **离线 APK**、断网可玩 | 1–1.5 天 |
| **O4** | 设备实测调优：线程数、`intra_op`、模型选择、首帧加载时间 | 真机帧率/耗时表 | 0.5 天 |

合计 **4–5.5 个工作日**（单机、不并发；不含 E-SLIM 若要先瘦身模型）。

## 5. 与联网版的关系

- **同一个前端页面**，零改动 —— 视觉与规则不会分叉（这是当初"不做离线版"的核心理由）。
- **两个 APK 两个包名**，可同时安装：
  - 联网版：`com.zhuoji.mahjong`（当前 v1.1.0）
  - 离线版建议：`com.zhuoji.mahjong.offline`，应用名 **「独山麻将·单机」**
- 离线版**不含**：对局历史云同步、冠军模型动态注册（模型烘焙进包）、局域网多人。

## 6. 建议的取舍（要你拍板）

1. **先做 E-SLIM 再打包离线版**：如果学生瘦身能把 9.85M 压到 1M 且非劣，
   离线包里 `champ` 的搜索档才可能可用；否则离线 v1 只带 **master + P48 贪心**。
2. **离线 v1 是否接受「无搜索档」**：贪心档在手机上就是 0.1–0.4 s/步，体验最好；
   搜索档在手机上是数十秒级，建议先不做。
3. **是否要「讲解」**（`reason.py`）：这是唯一需要额外移植 395 行的部分，可以二期。

> 本轮**没有**开始移植。若你确认继续，我按 O0→O4 推进，每阶段交付可验证的中间产物，
> 不做"看起来能跑"的半成品。
