# 训练 CPU 利用率分析（2026-10-11）

**结论先行：不是"资源没用上"，而是每轮有 ~450MB 的模型快照走管道 IPC，把 70% 的墙钟时间耗在了序列化/传输上。已修复并 A/B 验证（8.21s → 0.92s，轨迹逐元素一致）。**

## 1. 实测现象

机器：i7-14700K（8P+12E，20 物理核 / 28 逻辑核 / 32GB）。训练参数：
`--workers 12 --threads 24 --games-per-iter 96 --batch 512 --eval-every 10 --snapshot-pool s3,s7,s11`

| 指标 | 数值 |
|---|---|
| 每轮墙钟 | **10.4 s**（日志 `total` 差分） |
| 其中采集（日志 `collect`） | 1.2–1.6 s |
| 整机 CPU 均值 | **11%**（≈3.1 个逻辑核） |
| 24s 相位采样 | 训练进程 >4 核仅 8%，worker >2 核仅 20%，**72% 两边都闲** |
| 峰值 | worker 可冲到 11–12 核；主进程也可冲到 11–12 核 |

关键反差：**两边都有能力跑满，但 72% 的时间谁都没在跑。**

## 2. 根因：快照 IPC

每轮采集前，主进程把任务 pickle 给 12 个 worker。任务里除了主模型，还带
**常驻对手池（3 个银行快照）+ 训练内快照池（上限 8）= 11 份 state_dict**：

```
0.77M 参数 ≈ 3.1 MB/份 → 每任务 12 份 ≈ 37 MB
                        → × 12 worker ≈ 447 MB / 每轮
```

每轮 10.4s 里要完成 ~450MB 的 pickle → 管道写 → 管道读 → unpickle →
`_build_snap()` 重建 11 个网络。这一段：
- **单线程/低并行**（pickler、pipe 都是串行点），CPU 看起来很闲；
- 主进程在发、worker 在收，双方互等 → 表现为"两边都闲"；
- 每个 worker 还要重建 11 个 `nn.Module`，纯浪费（快照根本没变）。

A/B 实测（3 worker、5 份快照的轻量场景，8 局）：

| 路径 | 耗时 |
|---|---|
| 全量重发（旧行为） | **8.21 s** |
| worker 缓存命中 | **0.92 s** |

**9 倍差距。** 真实训练（12 worker、12 份快照）差距更大。

## 3. 次要因素

1. **采集与训练严格串行**：collect 1.3s 时主进程闲，update 时 12 个 worker 闲。
   即便没有 IPC 问题，瞬时利用率也只有一半。
2. **worker 落在 E 核**：逐核采样显示 12 个 worker 全在逻辑核 16–27（E 核区），
   8 个 P 核（0–15）几乎为 0。E 核单核性能约为 P 核的 6–7 成。
3. **小模型 + batch 512 的 CPU 训练并行度有限**：主进程请求 24 线程，
   实测均值只有 ~6.4 核的有效利用（约 27%），线程同步/内存带宽是瓶颈。
   这也是之前实测 24 线程是最优点（14→202ms、20→192、24→171、28→183）的原因。
4. **eval 阻塞**：每 10 轮跑 160 局评测（~31s），摊到每轮 3.1s，占总时间 ~30%。

## 4. 已实施的修复

`zhuoji/vcollect.py` + `scripts/selfplay.py`：**worker 侧快照缓存**。

- 快照在 selfplay 里只 append/裁剪、从不改写已存在的项 → 内容不可变；
- 主进程给快照池编号（`snap_epoch`），只在代数变化的那轮全量下发，
  之后各轮只发一个整数 key，worker 用本地缓存的快照网络；
- worker 缓存丢失（进程池每 150 轮重建、MemoryError 重建）→ 抛
  `_SnapCacheMiss` → 主进程自动全量重发一次兜底，**行为严格不变**；
- `--no-snap-cache` 可关掉缓存回到旧行为（A/B 对照用）。

**验证**：`scripts/verify_snap_cache.py` 两次采集（同 seed、同快照）轨迹逐元素一致、
reward 一致 → 缓存不改训练数据。

**预期收益**：每轮 10.4s → ~4–5s（**约 2× 吞吐**），CPU 利用率从 ~11% 提到 ~30–40%。
当前正在跑的 p_a_z 用的是旧代码（已加载进内存），**下一轮训练自动生效**。

## 5. 后续可做（按收益排序，未实施）

| 优化 | 预期 | 风险 |
|---|---|---|
| 采集/训练重叠（1 步策略陈旧，IMPALA 式） | +15–20% | 中：改算法语义，需重新验证 |
| eval 异步化（独立进程，与训练重叠） | −30% 墙钟 | 中 |
| `--workers 16` + 把 worker 摊到 P 核 | +10–15% | 低（内存 +2.7GB） |
| `--batch 1024` + `--games-per-iter 192` | 提高 CPU 每周期有效功 | 低（改样本分布，需重新验收） |

> 注意：这些都会改变"每轮看到的数据分布/时序"，按本项目的验收纪律，
> 任何启用都需要走一轮 roundrobin + paired duel 门控再晋升 master。
