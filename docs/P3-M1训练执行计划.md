## 0. 一页结论

**正式配方（冷启动，无 BC）** —— 下面是 **S1 段**的可直接复制命令（分段见 §4）：

```bash
python scripts/selfplay.py \
  --init models/dushan_master.pt \
  --arch m1 --encoder v3 --m1-preset m1 \
  --out models/dushan_m1_s1.pt --history reports/m1_s1_history.json \
  --rules dushan \
  --iters 800 --games-per-iter 192 --epochs-per-iter 1 --batch 512 \
  --lr 1.2e-5 --temperature 1.2 --teacher-prob 0.15 --past-prob 0.3 \
  --anchor-warmup 200 --kl-coef 0.02 --ent-coef 0.01 \
  --eval-every 20 --eval-rounds 40 --eval-anchor dushan_master \
  --select guard --select-metric vs_anchor \
  --save-every 20 --snapshot-pool dushan_master --snapshot-every 16 \
  --threads 24 --vectorized --workers 12 --seed 2026 \
  --pool-mem-pct 75 --pool-rebuild-every 150
```

> **`--out` 必须带段名**（`dushan_m1_s1` 而不是 `dushan_m1`）：检查点会落在
> `models/_ckpts/dushan_m1_s1_it*.pt`，段名自带 → 判读（`--ckpt-prefix`）与归档都不用猜。
>
> **`--pool-mem-pct 75`** 是 2026-10-12 新加的内存闸：**全系统**内存使用率 ≥ 75%
> （本机 23.85 GB）时主动重建进程池。原先只按固定 150 轮 —— 赌不起，见 §1.1 / §1.3。
> ⚠️ **判据必须是系统口径**：非训练占用（浏览器/编辑器）基线实测就有 **≈11.3 GB**，
> 若按"训练进程树 ≤ 物理内存 X%"判，训练树能涨到 22.9 GB（72%），那时系统总量
> = 11.3 + 22.9 = **34.2 GB > 31.8 GB → 直接 OOM**。第一版就踩了这个坑，已改。
>
> 随行起两个守护（各开一个终端，或在同一 shell 用 `&`）：
> `python scripts/keep_awake.py` 与
> `python scripts/res_monitor.py --interval 60 --out reports/_res_monitor_m1_s1.csv`

| 关键量 | 实测值 |
|---|---|
| 模型 | `dushan_m1` = SE-ResNet **160ch × 20** + Mish，**9,836,741** 参数 |
| 输入 | 编码器 **v3**：63 通道 / 130 全局维（七包全开 `abcdefg`） |
| 单轮 | **≈42 s**（采集 9.2 s + 更新 33 s），含 eval 摊入 ≈47 s |
| 吞吐 | **4.4 ms/样本**；一夜 11.5 h ≈ **885 轮 / 9.5 M 样本更新** |
| 三夜预算 | ≈ **2650 轮 / 28 M 样本** |
| 主门槛 | vs s11 共用牌池 1200 副配对净分差 **≥ +1.5 且 95% CI 下界 > 0** |

## 1. 机器复核（2026-10-12，用户确认 32 GB）

| 项 | 值 | 与旧口径的差异 |
|---|---|---|
| CPU | Intel i7-14700K | 不变 |
| 核心 | 28 逻辑 / 20 物理（8P+12E） | 不变 |
| 内存 | **31.8 GB（可 19.6 GB）** | 旧记忆里的"16 GB"是更早机器的口径，**已作废** |
| torch | 2.6.0+cpu | 不变（锁版本） |
| 指令集 | **AVX2**；`cpu_capability()=AVX2` | 无 AVX512-BF16 / 无 AMX |
| `bf16` | **比 fp32 慢 47 倍**（M1：23 327 ms vs 493 ms / step） | ⇒ **必须显式禁用 amp**，已写进 `net_m1.assert_no_amp()` 与避坑清单 |

**32 GB 实际解锁了什么**：12 个 worker（每个 ≈554 MB，含 8 份 M1 快照）合计 ≈6.6 GB，
加主进程 ≈2 GB，**总计 ≲9 GB** —— ⚠️ **此估算已被 2026-10-12 冒烟实测推翻，见下方勘误。**

---

### 1.1 ⚠️ 勘误（2026-10-12，冒烟实测）：内存是本轮的**头号约束**

`m1_plan_bench.py` 给出的 `est_per_worker_mb = 554` 是**短命压测**下的读数（进程刚起、
快照只有 8 份、跑几个 batch 就结束），**不代表长跑**。冒烟 200 轮的真实曲线（`reports/_res_monitor_m1_smoke.csv`）：

| 时刻 | 系统已用 | 备注 |
|---|---|---|
| 09:56（起跑） | 16.63 GB (52%) | 基线 |
| 10:21 | 21.15 GB (67%) | |
| 10:46 | 24.97 GB (79%) | |
| 11:10 | 28.43 GB (90%) | |
| **11:23** | **29.95 GB (94.2%)** | 贴着天花板 |
| 11:58 | 28.66 GB (90%) | |
| **12:00** | **20.02 GB (63%)** | ← **iter 150 进程池重建**放掉 ≈10 GB |
| 12:37 | 26.01 GB (82%) | 又开始爬 |

**结论（三条，都和老口径相反）**

1. **训练内存以 ≈6–9 GB/小时持续累积**，约 2 小时就顶到 90%+。空载基线约 11–12 GB
   （12:50 训练退出后实测 12.28 GB），即训练自身峰值占用 **≈18 GB**，可用余量只有 2–3 GB。
2. **`it % 150 == 0` 的进程池重建是唯一在维持这条命** —— 12:00 那次回落正是它。
   ⇒ 原文"进程池重建间隔可以从 150 轮放宽"**必须作废**；相反，S1 起跑前应实测
   「把间隔压到 80–100 轮」或「按可用内存低于阈值主动重建」，而不是放宽。
3. **旧监控有盲区**：`res_monitor.targets()` 只按 `cmdline[1]` 匹配脚本名，而 Windows
   下 spawn 出来的 worker 命令行是 `-c "from multiprocessing.spawn import ..."`，
   **一个都匹配不到**（实测系统 30.13 GB 时只认到主进程 3.32 GB）。
   已修：`targets()` 现在递归汇总**进程树** RSS，并新增 `tree_rss_gb` 列；
   `m1_segment_judge.py` 的 A5 改用「训练进程树峰值 / 机器物理内存」判据（阈值 70%），
   不再把浏览器等无关占用算在训练头上。回归：`scripts/_test_res_monitor_tree.py`。

**S1 起动前必须做**：跑 30 分钟观察 `tree_rss_gb` 峰值，若 >70% 物理内存则下调
`--workers`（12→8）或 `--games-per-iter`（192→96/128）后再放行长块。

### 1.3 ✅ 内存 30 分钟预检结论（2026-10-12 17:09，S1 完整配方 42 轮）

产物：`reports/_m1_precheck.out`、`reports/_res_monitor_m1_precheck.csv`（新监控口径，
`tree_rss_gb` 列有效）。

| 时刻 | 系统已用 | 训练进程树 | 树/物理 |
|---|---|---|---|
| 16:36 起跑 | 17.69 GB (55.7%) | 5.85 GB | 18.4% |
| 17:09 结束 | 22.23 GB (70.0%) | 10.96 GB | 34.5% |

**结论**

1. **训练进程树累积 ≈9.0 GB/小时**（5.85→10.96 GB / 34 分钟）；系统口径 ≈8.0 GB/小时。
   比冒烟期间的 6–9 GB/h 还快 —— 内存确实是这一段长跑的头号风险。
2. **非训练基线 ≈11.3 GB**（22.23 − 10.96）且基本恒定 ⇒ **判据必须用系统口径**
   （见 §0 的警告：按"训练树占比"判会在 34 GB 时才动手，那时已经 OOM 了）。
3. **外推**：按 `--pool-mem-pct 75`（= 23.85 GB），训练树涨到 ≈12.6 GB 时触发首次重建
   → 预计在**第 55–60 轮**（≈45 分钟），**远早于 150 轮兜底** ⇒ 内存闸是主导机制，
   轮数兜底基本不会触发。这正是"只按 150 轮赌不起"的实测证据。
4. **workers 维持 12**，不下调：采集只占单轮 1/4（collect 11.5 s / total 49 s），
   降到 8 会让采集涨到 ≈17 s（吞吐 −10%），而池重建已证明能放掉约一半内存
   （冒烟 3 次回落各 ≈8.6 GB）→ 不值得为省 2.8 GB 牺牲 10% 吞吐。
5. **训练侧健康**：42 轮全部 `kc=0`（处于 warmup 内，符合预期）、熵 2.076→1.968 平稳、
   `collect` 9.4→11.5 s 无冻结尖峰；末次 eval `avg_score` **−5.09**（冒烟同期 −5.66）、
   `vs_anchor` **−13.35**（40 副，噪声 ±1.5）—— 与冒烟同量级，符合"200 轮内追不上锚点"的预期。

## 2. 本轮发现并修复的 5 个真实缺陷（这些才是"最高效"的前提）

冒烟测试的价值在于它当场抓出了 5 个会让长训**静默变差**的问题。全部已修 + 有回归断言。

| # | 位置 | 症状 | 影响 | 修复与守卫 |
|---|---|---|---|---|
| 1 | `vcollect._worker` 缓存命中分支 | 末尾多一行 `snaps = [_build_snap(...) for sd in (snapshots_sd or [])]`，命中时 `snapshots_sd is None` → 把刚取出的缓存**覆盖成空列表** | 默认 `snap_key` 下**每 4 轮里有 3 轮完全没有历史快照在桌上**；league 自博弈名存实亡 —— 与 s9→s11 饱和、1200 轮 −0.159 完全吻合 | 删掉该行；`scripts/verify_snap_cache.py` 阶段 A 用 spy 直接断言"命中时对手池仍是 3 份" |
| 2 | `vcollect.collect_parallel` 兜底重发 | `sd_for_task = (snapshots_sd or []) if include_snaps else None` —— 调用方按约定在复用缓存的轮次传 `None`，兜底于是把**空池**当全量发下去 | 缓存未命中时对手池再次被清空（实测样本数 1163 → 1116，行为与"无对手池"完全一致） | 新增 `_SNAP_SENT_SD` 记住**真正发过**的载荷，兜底与单进程路径都用它 |
| 3 | `selfplay` 骨干换代 | 换代时沿用旧检查点的 `channels/blocks/hidden` —— master 里记的是 s 系列的 64/8/320 | 造出**"名字叫 M1、尺寸其实是 s11"** 的网络（实测参数量 818,717 而非 9,836,741），吞吐与容量双双错位 | 新增 `--m1-preset {m1,m0,m1l}`：冷启动且用户未显式指定宽度/深度时取预设；启动横幅打印 `arch/宽度/深度/输入维度` 便于当场核对 |
| 4 | `selfplay` 特征包解析 | 换代时 `--encoder-packs auto` 仍继承旧检查点掩码。master 是 v1、没有该字段 → 退回 **v2 的三包 `abc`** | **v3 的全部新特征（d/e/f/g，共 32 通道 / 32 维）被静默清零** —— 花大力气做的编码器等于没上 | 换代（版本或骨干变化）时 `auto` = 新版本全包；`encoder.py::parse_packs_for/pack_desc_for` 统一按版本解析 |
| 5 | `selfplay` 主进程线程 | `torch.set_num_threads` 只出现在 `collect_games`（非向量化路径）和 worker 内 | 向量化路径下**最耗时的 `update()` 用的是 torch 默认 20 线程**，`--threads 24` 对它无效（实测 24 线程比默认快 ~10%） | 主进程在建优化器前显式 `torch.set_num_threads(args.threads)` |

**新增两个必要旋钮**

- `--anchor-warmup N`：前 N 轮不做 KL 锚定，第 N 轮末把**当时**的策略冻结成锚点。
  冷启动必设 —— 否则锚点是一份**随机策略**，KL 惩罚往噪声上拽，且 `adapt_coefs` 会把 `kl_coef` 顶到 3.0 放大这个错误。
- `--snapshot-every N`（默认 4）：快照池一变就要给所有 worker 全量重发载荷 ≈ 份数 × 权重。
  s11 是 3.1 MB/份无所谓，**M1 是 39.3 MB/份**（8 份 ≈315 MB），必须把间隔拉到 16 来摊薄 IPC。

## 3. 最优并发配置：实测依据

| 决策 | 取值 | 实测依据 |
|---|---|---|
| 线程数 | **24** | M1 train step(b512)：8→2175 / 12→1711 / 16→1401 / 20→1351 / **24→1222** / 28→1375 ms |
| workers | **12**（⚠️ 受内存约束，见 §1.1） | 采集段 192 局仅 9.2 s，远低于 update 的 33 s，**再加 worker 对吞吐没有意义**；而 worker 越长越涨内存（压测的 554 MB/worker 不代表长跑）→ 内存吃紧时**优先下调 workers** |
| games-per-iter | **192** | 每轮固定开销靠规模摊薄：48→5.4 / 96→4.6 / **192→4.4** ms/样本 |
| batch | **512** | 512 / 1024 / 2048 的 update 吞吐**完全相同**（3.20 / 3.16 / 3.22 ms/样本） |
| epochs | **1** | update 是瓶颈（占 2/3），多 epoch 只是把同一批数据重复算 |
| 共享内存传权重 | **不做** | 实测无收益（4.59 s vs 4.60 s），已否掉 —— 省下的复杂度比收益值钱 |

**瓶颈定位**：`update()` 占单轮的 **2/3**（33 s / 42 s）。所以任何"加并行度"的努力都是白费；
要再提速只能：① 减少每轮样本数换更多轮（总样本不变）；② 让采集与更新**重叠**（1 步陈旧策略，见 §6 后手）。

### 3.1 一个尚未定论的疑点：更新段真的吃满 24 线程了吗

冒烟期间对训练**主进程**做 2 秒粒度 CPU 采样，60 秒内得到：

```
 77  78  54   0   0   0   0   0 159 728 713 698 684  62  94  61  78  62  97  57  76 149  80  70  55  68  16   0   0   0
```

大量窗口在 **0%**（主进程阻塞、等 worker 采集），而真正在算梯度的窗口只有
**684–728%（约 7 个核）** —— 但命令行给的是 `--threads 24`。这与"更新段 = 24 线程满负荷"
不符，**可能意味着更新段还有 2–3× 余量**。

已知的**方向性证据**（墙钟，`--threads 8 → 24`）：

| 线程 | wall s/step | 相对 8 线程 |
|---|---|---|
| 8 | 3.070 | 1.00× |
| 16 | 2.053 | 1.50× |
| 24 | 1.911 | **1.61×** |

即多给线程有收益，但**远非线性**（24 线程理论应接近 3×）。若能把有效并行度从 ~7 提到 ~20，
单轮可从 42 s 降到 ~25 s，四段预算整体重写。

**所以加了一条前置动作**：在冒烟结束、S1 起动前的空窗里跑

```bash
python scripts/probe_threads.py --variants default,channels_last,pin_p,pin_p_cl \
       --threads-list 8,16,24,28 --reps 3 --json reports/probe_threads.json
```

它比较三种可能拿到余量的手段：`channels_last`（CPU conv 走 oneDNN 通道后置布局）、
绑 8 个 P 核（逻辑 0–15，避免被 12 个 E 核拖着调度）、以及二者叠加。
**必须在机器空闲时跑** —— 带着训练进程测会被线程争抢污染（实测 wall 膨胀 3 倍、并行度读数不可信），
脚本已内置忙碌检测与 `--force` 逃生门。

### 3.2 ✅ 探针结论（2026-10-12 16:25 已跑）：**没有免费提速，"7 核"的猜想被证伪**

`python scripts/probe_threads.py --variants default,channels_last,pin_p,pin_p_cl --threads-list 8,16,24,28 --reps 3`
（空闲机器）→ `reports/probe_threads.json`、`reports/_probe_threads.out`。

wall s/step（batch 512，越小越好）：

| 变体 | 8 | 16 | **24** | 28 |
|---|---|---|---|---|
| **default（contiguous）** | 3.153 | 1.905 | **1.664（1.89×）** | 2.386 |
| channels_last | 3.458 | 2.162 | 1.812（1.91×） | 2.619 |
| pin_p（绑核 0–15） | 3.846 | 3.460 | 5.921 | 6.664 |
| pin_p_cl | 4.332 | 3.915 | 6.141 | 7.137 |

**判读**

1. **`channels_last` 没有收益**：任一档位都不比 contiguous 快（24 线程 1.812 vs 1.664）→ 不采纳。
2. **绑 P 核是负优化**：24/28 线程时 wall 反而是 default 的 3–4 倍（±48–69 cpu-s/wall，
   典型超订程争抢）→ 说明 **E 核在帮忙，不该被排除**。不采纳。
3. **`--threads 24` 依然是当前最优，扩展比 1.89×** —— 与 §3.1 用墙钟法测到的
   1.61×（8→24）同一量级。⇒ **§3.1 里"有效并行度只有 ~7 核、可能还有 2–3× 余量"的猜想不成立**，
   那段 CPU 剖面（684–728%）应是采样窗口与 update/collect 交替造成的假象。
4. ⇒ **单轮 ≈42 s、三夜 ≈2650 轮的预算不用改**；S1 原样起跑，`selfplay` 更新段一行都不用动。

> 副作用提醒：探针里的"有效并行度"列（cpu/wall）读数不稳定（8 线程出现 0.87、16 线程出现 0.45，
> 即 cpu < wall），说明 `time.process_time()` 在这台机器上的多线程口径不可靠 ——
> **只看 wall 列**，别用 cpu 列下结论。

## 4. 分段执行计划（每段 1 夜，段间验收）

| 段 | 轮数 | 配方差异 | 累计样本 | 段末动作 |
|---|---|---|---|---|
| **S0 冒烟** | 200 | 上述配方原样 | 2.1 M | 已在跑；确认 s/iter、熵稳定性、对手池生效 |
| **S0.5 探针** | 0 | 只跑 `probe_threads.py`（需空闲机器） | — | ✅ **已跑**：`channels_last`/绑 P 核**均无收益** → 更新段不动，S1 原样起跑（§3.2） |
| **S1** | +800 | 同 S0；`--out models/dushan_m1_s1.pt`；**`--anchor-warmup 200`**（冷启动必须 —— 冒烟已证不设则锚在随机策略上） | 10.6 M | 段末 1200 副配对复评 vs s11 → 必须**不显著劣于 s11**（冷启动期的合理下限） |
| **S2** | +800 | **续跑**：`--init models/dushan_m1_s1.pt --out models/dushan_m1_s2.pt`；**`--anchor-warmup 0`**（锚点已存在，别再放开 200 轮）；`teacher-prob 0.15→0.08`、`temperature 1.2→1.0` | 19.1 M | 段末复评 → 必须**显著优于 S1 的 checkpoint**（说明还在涨） |
| **S3** | +850 | **续跑**：`--init models/dushan_m1_s2.pt --out models/dushan_m1_s3.pt`；**`--anchor-warmup 0`**；`teacher-prob 0.05`、`lr 1.2e-5→6e-6` | 28 M | 段末复评 → 主门槛 `≥+1.5 且 CI 下界>0` → 晋升 master |

> **`--anchor-warmup` 的分段陷阱**（2026-10-12 修正）：它是**每次重启都重算**的 —— 若四段都写
> 200，等于共 800 轮（≈11 h）处于"无 KL 锚定"状态。**只有 S1（冷启动）该给 200**；
> S2/S3 续跑时锚点已经在检查点里，必须写 0。

**为什么分 4 段而不是一条 2650 轮的长跑**：本项目两次事故（22.2 h 睡眠冻结、s9 因 nohup 脱管失联）

   同时 `tree_rss_gb` 列会在 `--pool-mem-pct` 触发时给出那次重建的内存证据。
3. **段末**：`python scripts/m1_segment_finalize.py --run <段名> --ckpt-prefix <前缀>`

   判读默认 1200 副、`--extra dushan_big_s11`（M1 的主门槛就是 vs s11）。

### 1.2 冒烟模型（`dushan_m1_smoke.pt`）的去留

200 轮冒烟的两个观测：

- **`avg_score` 确实在涨**：−5.66 → −4.1~−4.9（中期最好），末轮回落 −5.66；`R`（回报）从 −0.147 升到 ≈0；
- **`vs_anchor` 完全没动**：全程 −11.4 ~ −14.6，且 10 次评测彼此都在 ±1.3 的噪声带内 —— **对 `dushan_master` 零追赶**。

⇒ 结论：**冷启动的 M1 在 200 轮尺度上还没进入"接近锚点"的区间**，这本就在预期内（S1 的门槛只是
"不显著劣于 s11"，主门槛在 S3）。所以冒烟模型**不够格晋升**，但它是一个合法的**热启动起点**
（已花掉的 2.1 M 样本不必重算）。两种走法：

- **A 冷启动（推荐，照 §0 原配方）**：`--init models/dushan_master.pt`。好处是与计划的
  "冷启动门"口径一致、可归因；代价是重算 200 轮（≈2.8 h）。
- **B 热启动**：`--init models/dushan_m1_smoke.pt --anchor-warmup 0`。省 2.8 h，
  且冒烟的 2.1 M 样本不白费。**注意必须配 `--anchor-warmup 0`**（理由见下）。

**必须注意：KL 锚点不持久化**（2026-10-12 查证 `selfplay.py:644`）
`ref_model = copy.deepcopy(model)` 发生在**每次启动**，而且**不写进检查点**。所以
续跑时锚点会自动等于 `--init` 的那份权重，`--anchor-warmup` 也每段重算：

- **冷启动（A）**：`--init` 的权重因骨干换代被跳过 → `model` 是随机初始化 → 锚点是随机策略
  → **必须 warmup >0**（否则 KL 往噪声上拽，`adapt_coefs` 还会把 `kl_coef` 顶到 3.0）。
- **热启动（B）**：`--init models/dushan_m1_smoke.pt` → 锚点自动 = 冒烟末轮策略（有意义）
  → **warmup 应写 0**，否则白放 200 轮不锚定。
- **S2/S3 续跑**：同理一律 **warmup 0**。四段都写 200 的话，共 800 轮（≈11 h）没有 KL 锚定
  —— 那是纯粹的算力浪费。

**段末一条命令完成验收**

```bash
# 训练结束后（或另开一个终端，判读当前已完成的部分）
python scripts/m1_segment_judge.py --run m1_s1 --deals 1200 --threads 24 \
       --extra dushan_big_s11
```

它把两道门合成一次输出：

- **阶段 A 健康度**（秒级）：熵带宽/坍缩、`collect` 离群、每轮真实 wall 时间的冻结尖峰、
  监视器打点空洞、内存峰值、**对手池活体检查**、KL 锚点预热、样本量量级。
  三态结论 PASS / FAIL / **SKIP**（数据不足不计入总判，避免跑到一半时虚报一堆 FAIL）。
- **阶段 B 真实强度**（分钟级）：自动取 `models/_ckpts/<run>_it*.pt` 均匀抽样到
  `--max-ckpts` 个，加 `--extra` 的外部参照，跑**共用牌池 + 共用对手**的 4 座位轮换配对赛，
  直接给出"各点 vs 本段首点"的净分差与 95% CI。结果写 `reports/{run}_judge.json`。

> 存档点匹配用 `{run}_it*.pt` **精确**模式 —— 用 `{run}*` 会让 `dushan_b2_p_a`
> 顺手吞掉 `dushan_b2_p_abc_it*`，把两个消融臂混进同一场配对赛。
>
> 判读脚本**不会**在找不到 `_res_monitor_{run}.csv` 时回退到共享 CSV：宁可报
> "缺数据"，也不能把上一次长跑的读数当成本次的。
