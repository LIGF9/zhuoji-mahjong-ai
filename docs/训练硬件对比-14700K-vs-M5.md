# 训练硬件对比：i7-14700K（无独显） vs MacBook Air M5 32GB

> **数据可信度声明**：本文的 M5 规格取自 Apple 官方技术规格页（M5：10 核 CPU
> = 4 性能核 + 6 能效核、10 核 GPU、16 核神经引擎、**153 GB/s** 统一内存带宽、
> 无风扇被动散热）。网上大量「M5 训练比 RTX 4090 快 12%」之类的文章来自
> SEO 内容农场，数字互相矛盾且无法复现，**本文不采信**。对你这个项目的结论
> 请以你机器上 `scripts/bench_scale.py` 的实测为准。

---

## 0. 结论先行

| 使用方式 | 谁更快 | 差距（估计） |
|---|---|---|
| **纯 CPU 训练**（现状代码，不改） | **14700K 明显赢** | 2–3× |
| MPS/GPU 训练（需改代码），短时 | M5 可能赢 | 1.5–2.5× |
| MPS/GPU 训练，**长时间**（值班链 7 h 那种） | 打平或 14700K 略优 | 0.9–1.5× |
| 便携性 / 随时开干 / 短实验 | M5 完胜 | — |

**对这个项目，14700K 台式机更合适。** MacBook Air 的定位应该是「便携开发机 +
P1 阶段 0/1 的短实验机」，不适合当长时间训练主机 —— 原因是下面第 3 节的
「无风扇」和「只有 4 个性能核」这两条硬约束。

## 1. 规格对照

| | i7-14700K | Apple M5（MacBook Air） |
|---|---|---|
| CPU 核心 | **8 P + 12 E = 20 核 / 28 线程** | 4 P + 6 E = 10 核 / 10 线程 |
| 全核频率（估） | P 5.3 GHz / E 4.3 GHz | P ~4.6 GHz / E ~2.9 GHz |
| 内存带宽 | DDR5-5600 双通道 ≈ 89.6 GB/s | **153 GB/s**（统一内存） |
| GPU | 无独显（核显对训练无用） | 10 核 Apple GPU + 每核神经加速器 |
| 散热 | 台式，可无限期满载 | **无风扇，被动散热** |
| PyTorch 后端 | CPU（oneDNN / MKL） | CPU（Accelerate）或 **MPS** |
| 内存 | 通常 32–64 GB DDR5 | 32 GB 统一内存 |

### 两个「看起来很美但用不上」的点

1. **153 GB/s 带宽对 10M 网络毫无意义**。10M 参数 fp32 权重才 40 MB，加上
   Adam 状态和激活值总需求 < 2 GB，任何一台机器都装得下，带宽完全不是瓶颈。
   统一内存的优势要到上百亿参数才体现。
2. **核数差距是硬的**。CPU 训练吃的是「有多少个能跑 AVX2/NEON FMA 的性能核」：
   14700K 有 8 个 P 核，M5 只有 4 个。E 核在 FP32 矩阵运算上很弱，指望不上。

## 2. 三种方式分开算

### 2.1 纯 CPU（不改代码）

FP32 理论峰值粗算：

| | 计算 | 峰值 |
|---|---|---|
| 14700K | 8 P 核 × 16 FLOP/cyc × 5.3 GHz + 12 E 核 × 8 × 4.3 GHz | ≈ **1.1 TFLOPS** |
| M5 | 4 P 核 × 8 FLOP/cyc × 4.6 GHz + 6 E 核 × 4 × 2.9 GHz | ≈ **0.22 TFLOPS** |

即便考虑 Apple 的 AMX 矩阵协处理器可能通过 Accelerate 被 PyTorch 用上（这点
不确定，且 AMX 主要吃低精度），M5 在**核数**上仍是 14700K 的一半以下。

**估计 M5 纯 CPU ≈ 14700K 的 30–50%**。换算到 10M 网络：

- 14700K：约 27–32 s/轮 → M5 纯 CPU：约 **65–100 s/轮**

### 2.2 MPS/GPU（需要改代码）

M5 GPU 10 核的 FP32 峰值约 4 TFLOPS（理论上比 14700K 的 CPU 高得多），
**但有两个打折项**：

**打折项一：模型太小，GPU 吃不饱。**
这个网络的特征图只有 `3 × 9 = 27` 个空间位置，卷积核 3×3。单次 conv 的矩阵
规模很小，kernel launch 开销和低占用率会吃掉大部分理论算力。这正是为什么
当前 0.77M 网络在 CPU 上单 batch 只要 ~500 ms —— 计算量本身就不大。
**真正能喂饱 GPU 的是 P3 阶段放大到 10M 之后**（通道 160+、batch 512+）。

**打折项二：只有 80% 的工作能被加速。**
每轮的时间构成是：

```
采集（96 局自对弈，纯 Python 引擎，单核 CPU 密集）  ≈ 2.0 s   ← GPU 帮不上
更新（前向 + 反向 + Adam）                          ≈ 7.6 s   ← 可上 GPU
```

而且 **P3 阶段必然要把 `--games-per-iter` 提到 300–500**（大网络需要更多样本），
那时采集时间会**线性放大到 6–10 s/轮**，而这部分在 Mac 上只能靠 4 个 P 核，
**会变成真正的瓶颈**。

### 2.3 长时间训练的致命项：无风扇

MacBook Air 是被动散热。满载训练十几分钟后芯片温度升高，会触发降频保护，
持续性能通常掉到峰值的 50–70%（MacBook Pro 有风扇，不受此限；Mac Studio 更不
受影响）。而你的训练场景恰恰是**长时间满负载**：

- 7 小时值班链（`scripts/shift_chain_*.py`）
- P1 阶段 3 计划连续跑 8 小时
- P3 阶段要连续跑几天

**短时跑分 Mac 可能好看，长跑会被 14700K 反超或追平。**

## 3. 汇总估算表

| 场景 | 14700K（估） | MacBook Air M5（估） | 谁快 |
|---|---|---|---|
| 0.77M，纯 CPU，10 min | 9.5 s/轮 | 20–30 s/轮 | 14700K 2–3× |
| 0.77M，MPS，10 min | 9.5 s/轮 | 4–7 s/轮 | M5 1.4–2.4× |
| 0.77M，MPS，**连续 4 h** | 9.5 s/轮（稳定） | 7–12 s/轮（降频后） | 打平~14700K |
| 10M，纯 CPU | 27–32 s/轮 | 65–100 s/轮 | 14700K 2–3× |
| 10M，MPS，**连续 4 h** | 27–32 s/轮 | 15–30 s/轮（降频后） | 打平~M5 1.5× |
| 采集（P3，500 局/轮） | 5–7 s/轮 | 8–12 s/轮（4 P 核） | 14700K 1.5–2× |

**所有数字都是估算，必须实测。** 到 Mac 上第一件事：

```bash
python scripts/bench_scale.py --device mps --threads 4 --json bench_m5.json
python scripts/bench_scale.py --device cpu --threads 10 --json bench_m5_cpu.json
```

与本项目已有的旧机器实测表（见 `docs/迁移到新机器.md` §1）对比，就知道真实加速比。

## 4. 如果真要在 Mac 上训练：改造清单

当前代码是 CPU-only 的。要让 MPS 跑起来，需要这些改动（按重要性排序）：

| # | 改动 | 说明 |
|---|---|---|
| 1 | **设备抽象** | `selfplay.py` 加 `--device {cpu,mps}`；`model.to(device)`；张量创建时指定 device |
| 2 | **MPS 算子兜底** | 设 `PYTORCH_ENABLE_MPS_FALLBACK=1`，不支持的算子自动回退 CPU（会拖慢但可用） |
| 3 | **采集与训练分离** | 多进程采集（`mp.get_context("spawn")`）在 macOS 上本来就与 Windows 行为一致，**无需改动**；但要确保 worker 只做 CPU 推理（不要把模型搬到 MPS 再 fork） |
| 4 | **worker 数** | 从 4 调到 4（正好用满 4 个 P 核）；`--threads` 只在 CPU 侧生效 |
| 5 | **batch 调大** | MPS 上小 batch 的 launch 开销占比高，`--batch` 从 512 试到 1024–2048 |
| 6 | **防休眠** | `ctypes.windll`（Windows API）在 macOS 无效 → 改用 `caffeinate -i -t <秒>` 包住训练子进程 |
| 7 | **路径** | `scripts/migration_bootstrap.py --fix-paths` 已能自动把 `PY` 与 `ROOT` 改成当前机器实际值（Mac 上就是 macOS 路径），无需手工改 |
| 8 | **MPS 不支持 fp64** | 检查代码里没有 `.double()`；损失/统计尽量用 fp32 |

> 第 6、7 项是**必做**的，否则值班链在 Mac 上直接跑不起来。

## 5. 建议

按你的实际目标排优先级：

1. **如果只能买一台**：选 **14700K 台式机**。这个项目要的是「长时间稳定满载」，
   这正是台式机的主场、MacBook Air 的短板。10M 网络在它上面 27–32 s/轮，
   10 代 ≈ 3–4 天，够用。
2. **如果还想更进一步**：在 14700K 上**加一张 16 GB 显存的显卡**，这才是唯一能
   一次性解决所有问题的方案 —— 10M 网络可降到 **< 1 s/轮**，一天跑几万轮，
   P3 阶段的「百万局级自对弈」才真正可行。CPU 路线能跑通、能看见趋势，但想逼近
   职业水平，算力迟早是第二瓶颈。
3. **如果 MacBook Air 已经买了/必须用**：把它当**便携开发机 + 短实验机**
   （P1 阶段 0/1、跑对局、写代码、看网页），长训练放台式机。这样分工其实很合理：
   Mac 上做设计和快速验证，台式机上挂长跑。
4. **如果考虑别的 Mac**：要当训练主力，至少得是**有风扇**的 MacBook Pro，
   或者干脆 Mac Studio（M5 Max，GPU 核心多得多，散热也好）。MacBook Air
   无论内存多大，都不是长时间训练的正确形态。
