# P3：10M 参数模型设计（目标：显著超越 big_s11）

> 日期：2026-10-12 ｜ 状态：设计稿（待评审）
> 基线：`dushan_big_s11.pt`（64/8/320，0.77M 参数）＝当前 `dushan_master.pt`
> 候选名：`dushan_m1.pt`（M = Mega / Mortal-style）

---

## 1. 背景与问题定义

**现状证据（三条独立证据，为什么 0.77M 已经到顶）：**
1. 3000 副配对天梯：s9/s10/s11 两两无显著差异（`README.md:833-847`）；
2. **10-12 夜跑实测（新增，最硬的一条）**：`s11 + 1200 轮` = **−0.159**；`400 轮` ≈ `1200 轮`（−0.114 vs −0.159，CI 内）。**延长训练不但没有收益，还在缓慢退化**；
3. 双阶段特征消融（P1/B/C 阶段）全部增量 ≤ CI 半宽（±0.27），a+c 包在 1200 轮长预算下的纯净贡献仅 **+0.176**（CI 半宽 ~0.43，读不出来）。

三条证据共同指向：**瓶颈是容量/表征，不是训练预算**。这正是把 0.77M 放大到 10M 的决策依据。判读详见 `reports/夜跑判读-plan_b_bc_long-2026-10-12.md`。
- 用户目标：10M 参数级模型，在 1200 副配对净分差口径下**大幅**超过 s11（不止 +0.40 门槛，目标 ≥ +1.5，即 3~4 倍门槛）。

**约束：**
- 纯 CPU 训练与推理（torch 2.6.0+cpu），16 GB 内存，Windows。
- 已有资产必须复用：v2 编码器（31ch/98glob，v1 严格超集）、三头动作空间（discard 28 / self_kong 28 / respond 4）、向量化 selfplay 管线（`scripts/selfplay.py` + `zhuoji/vcollect.py`）、BC 预热管线（`train_bc.py --freeze-old` + `verify_bc_warm.py`）、评估栈（`score_checkpoints.py` / `roundrobin.py` / `duel.py`）。

## 2. 文献检索结论 → 采纳决策

| 工作 | 核心思想 | 对本设计的决策 |
|---|---|---|
| **Suphx**（MSRA, arXiv:2003.13590）天凤十段 | ① Oracle guiding：训练时喂完美信息，逐步 dropout 到常规观测；② 全局奖励预测（GRU 预测终局奖励作中间信号）；③ 5 个 CNN 决策点网络 + pMCPA 运行时适应 | ① **采纳（第二阶段，PTIE 形式）**；② 不需要——独山每局终局即结算，回报不稀疏；③ 不采纳——统一单网 + 头掩码已验证更简单，pMCPA 推理太贵 |
| **Mortal**（Equim，天凤最强开源 AI）v2-v4 | ResNet 40 blocks × 192 ch ≈ **10.8M 参数** + **通道注意力（SE）** + dueling DQN 头 + Mish/BN(eps=1e-3)；GRP 模型给训练奖励 | **架构主蓝本**。证明 ~10M 恰是麻将 CNN 的甜点区。SE 注意力便宜且有效；BN eps=1e-3 采纳（小空间网格上 BN 统计噪声大）。其 40×192 是 4090 GPU 训练，我们 CPU 上按算力缩到 20×160 |
| **PerfectDou**（网易，arXiv:2203.16406） | PTIE（完美训练-不完美执行）：**critic 看全局信息，actor 只看合法观测**，训练样本效率比 DouZero 高 10 倍；稠密 oracle 奖励 | **采纳 PTIE-critic**（第二阶段）：oracle 通道只进价值头，策略头路径与部署完全一致——避免 Suphx 全网 dropout 的分布漂移风险 |
| **DouZero**（2021） | 深度蒙特卡洛 + 矩阵化动作编码，处理超大动作空间 | 已被现有三头设计覆盖（动作空间小，无需借鉴） |
| **Reevaluating PG Methods for IIG**（arXiv:2502.08938, 2025，5600+ runs） | **通用策略梯度（PPO/A2C）与 CFR 系方法在大型隐信息博弈上打平或更优**，FP/DO/CFR 系无一胜出 | **背书现有 A2C 自博弈骨架不换算法**——保持 REINFORCE+价值基线+KL 锚定，把算力花在容量与特征上，不冒 CFR 化的工程险 |
| **QFR**（ICLR 2025） | 策略梯度首次获得 best-iterate 收敛保证 | 理论方向正确但基于表格设定 + 需要重写更新器，**暂不采纳**，记录为后手 |
| **Ataraxos**（arXiv:2511.07312, Stratego 超人类） | 自博弈 RL + **测试时搜索**（隐信息下），算力/样本比前人低几个量级 | 测试时搜索在 CPU + Web 实时约束下不可行，**记录为后手**；但其"低算力超人类"路径证明本设计的小算力前提是现实的 |
| **GO-MCTS / LAMIR**（2024/2025） | 观测空间 MCTS / 学习模型前瞻推理 | 依赖生成模型或抽象模型，工程复杂度高，**不采纳** |

**一句话综合**：2020-2026 的证据链 = *「架构上：ResNet+SE 甜点区 ~10M；训练上：actor-critic 自博弈仍是主力；信号上：critic 吃完美信息（PTIE）是样本效率最大单项增益；执行上：只部署 actor」*。本设计严格沿此路径。

## 3. 模型设计：`dushan_m1`

### 3.1 编码器 v3（`zhuoji/encoder_v3.py`，v2 严格超集）

沿用 v2 的零初始化/包掩码纪律（P1 消融的教训：热启动新通道必须零初始化）。

**观测平面 31 → 63 通道**（新增 32 通道）：

| 通道 | 内容 | 依据 |
|---|---|---|
| 31-33 | **横鸡轮状态**：按 27 牌种压缩为 3 平面——①该牌种横鸡轮是否开放 ②开启者相对座位 ③轮内已跟进张数 | 横鸡轮是独山核心博弈点，目前完全不进特征（`encoder.py` 只留 g[31-34,74-77] 间接统计） |
| 34-38 | **各家牌河分花色热图**（万/条/筒 3 张数）+ 峰值巡目 | 辅助读牌 |
| 39-46 | **各家最近 5 张弃牌独热**（4 家 × 2 通道：牌 one-hot 压缩 + 打出时巡目） | 比 v2 的"最近 1/2/3 张"更长时序，防御/读牌关键 |
| 47-54 | **8 番型逐家可行性平面**（由 v2 的 g[86-93] 全局维升级为逐家 27 格平面，编码其结构位置） | 大牌攻防判断 |
| 55-62 | **包赔风险平面**：对每家编码"若其胡则我可能包杠/包鸡/包大牌的持牌暴露度" | 包赔规则是独山独有激励，现在只有 g[96] 一个标量 |

**全局维 98 → 130**（新增 32 维）：横鸡轮全局计数、四家立直式宣言状态、本局已发生的番型事件计数、杠墙进度、鸡牌全种持有矩阵展平（自己 + 全场亮明，27×2 压缩为 24 维）等。

**Oracle 通道（仅 PTIE-critic 用，不进 actor 路径）**：3 家手牌各 1 通道 + 牌墙余牌 1 通道 = 4 通道，作为独立小分支输入价值头（见 3.3）。

### 3.2 骨干（`zhuoji/net_m1.py`）

```
tiles (B, 63, 27) → reshape (B, 63, 3, 9)
stem:  Conv3x3(63→160) + BN(eps=1e-3) + Mish
20 × [ ResBlock: Conv3x3(160→160)+BN+Mish → Conv3x3(160→160)+BN
       + SE(160, r=16) 通道注意力 ]          ← Mortal v2+ 同款
avgpool → concat(glob 130) → FC(290→512) → Mish → FC(512→512) → Mish
四个头（与现有完全同构）：discard 28 / self_kong 28 / respond 4 / value 1
```

- **激活函数 Mish**：Mortal v2+ 实证优于 ReLU（同参数量下），风险低。
- **BN eps=1e-3**：3×9 小网格上批统计噪声大，Mortal 经验。
- **SE 注意力**：每 block 仅 ~2.7K 参数，让 20 层深度真正发挥作用。

### 3.3 PTIE Oracle-Critic（第二阶段启用，先留接口）

- oracle 分支：`4ch×27 → Conv3x3(4→32) → Conv3x3(32→32) → avgpool` ≈ 0.04M 参数；
- 价值头输入 = `concat(trunk 512, oracle 32) → FC(544→1)`；
- 采集时 value 用完整输入（自博弈内部本来可见全局）；**部署/对评时 oracle 分支置零**，与 PerfectDou 的 PTIE 一致——策略头参数路径与部署完全一致，无分布漂移；
- 消融纪律：M1-A（无 oracle）与 M1-B（有 oracle）两臂对比，只差这一个变量。

### 3.4 参数预算与算力物理约束（解析核算 + 实机微基准）

**先记住一条硬约束**：27 格（3×9）网格上 **卷积 MACs ≈ 27 × 卷积参数量**（每个权重只被 27 个位置复用）。
因此「换卷积核 / 换深度可分离」都逃不掉算力——深度可分离把参数和 MACs 同比例缩减，比值不变（实测 0.037 vs 0.037）。
唯一有意义的架构结论：**3×3 核在花色边界上会跨行（万9 与 条1 相邻）语义有误**，纯纵向 `(1,3)` 核更合理且参数量/MACs 同步降 3×，但需要更宽的网络才能花掉 10M 预算——记录为**一号消融备选**，不作为首发配置（首发保持与 Mortal 同族的 3×3，减少变量）。

| 配置 | 参数量 | 单次前向 MACs | vs s11 算力 |
|---|---|---|---|
| s11 big 64/8/320（31ch/98g） | 0.79M | ~17M | 1× |
| **M1：160/20/512 + SE（63ch/130g）** | **9.84M（实测实例化）** | ~252M | **~6.4×（实测 fwd+bwd）** |
| 变体 B：192/16/512 | 11.20M | 34M/块口径，超预算，弃 | — |
| 变体 C：128/32/512 | 9.97M | 备胎（更瘦更深） | — |
| 变体 E：224/24 `(1,3)` | 7.92M | 197M | 一号消融备选 |

核验脚本：`scripts/bench_net_throughput.py`（可复现，含 fwd/bwd、eval(b64)、eval(b1) 三档计时）。

### 3.5 推理延迟（实机实测）

`scripts/bench_net_throughput.py`，24 线程：

| 场景 | s11 | M1（9.84M） |
|---|---|---|
| 单样本批量前向（batch 64 摊薄） | 0.47 ms | 1.64 ms |
| **单步推理（batch 1）** | 7.79 ms | **21.3 ms** |

→ Web UI 端到端仍远低于 1s 约束，**不需要量化/蒸馏**；采集端批量前向 2.6× 开销可接受（见 §4.0）。

## 4. 训练配方

### 4.0 吞吐预算（★ 2026-10-12 已按 M1 **实机实测**重写，此前所有估算作废）

实测环境：i7-14700K（**28 逻辑核 / 20 物理核**，8P+12E）、**31.8 GB RAM**、torch 2.6.0+cpu、**仅 AVX2**。
脚本：`scripts/m1_plan_bench.py`（结果 `reports/m1_plan_bench.json`）。

**(a) 线程扩展（M1 9.84M，batch 512）**

| 线程 | 8 | 12 | 16 | 20 | **24** | 28 |
|---|---|---|---|---|---|---|
| train step (ms) | 2175 | 1711 | 1401 | 1351 | **1222** | 1375 |
| 样本/s | 236 | 299 | 365 | 379 | **419** | 372 |
| eval b64 (ms) | 128 | 114 | 124 | 122 | **109** | 137 |

→ **取 24 线程**（比 torch 默认的 20 快约 10%；28 线程反而退化，因为超过物理核数）。
**注意**：向量化路径下 `update()` 跑在**主进程**，而主进程的线程数在本次修复前从未被设为
`--threads`（用的是 torch 默认 20）。已在 `selfplay.py` 显式补上。

**(b) 采集（12 workers，复用进程池）**

| 规模 | worker 内耗时 | 主进程墙钟 | ms/样本（采集段） |
|---|---|---|---|
| 48 局 | 4.35 s | 4.59 s | 1.70 |
| **192 局** | 8.91 s | **9.20 s** | **0.86** |

一次性的进程池冷启（12 × spawn + 建网）≈ **3.9 s**，只在第一轮付。
**共享内存传 state_dict 无收益**（4.59 s vs 4.60 s）—— 39 MB 权重经管道传输并不是瓶颈，已实测否掉。

**(c) 更新（`update()`，epochs=1，24 线程）**

| batch | 512 | 1024 | 2048 |
|---|---|---|---|
| 10734 样本用时 | 34.3 s | 33.9 s | 34.5 s |
| ms/样本 | **3.20** | 3.16 | 3.22 |

→ **batch 对吞吐无影响**，保持 512（与历史口径一致，便于对比）。**`update()` 是绝对瓶颈（占 2/3）。**

**(d) 训练内评测成本（M1 vs 锚点 s11，每副 4 座轮换）**

| eval-rounds | 20（80 局） | 40（160 局） | 60（240 局） |
|---|---|---|---|
| 单次耗时 | 33.0 s | 65.8 s | 100.4 s |

→ **取 40 轮 + eval-every 20**（摊入 ≈ 3.3 s/轮，占 7%）。

**(e) 内存**

M1 权重 **39.3 MB/份**（s11 是 3.1 MB，13 倍）。估算单 worker = 运行时 ~200 MB + 快照 8×39.3 + 主模型 39.3 ≈ **554 MB**；
12 workers ≈ **6.6 GB**，加主进程（模型+梯度+AdamW+ref+8 快照）约 1.5–2 GB，**合计 ≲ 9 GB**，在 32 GB 下余量充足
（这也是"32 GB 解锁了什么"的答案：可以用满 12 workers 而不用担心 16 GB 时代的累积崩溃）。

**(f) 全轮吞吐（实测，g = games-per-iter）**

| g | collect | update | eval 摊入 | 合计 | ms/样本 | 一夜 11.5 h 轮数 | 样本/夜 |
|---|---|---|---|---|---|---|---|
| 48 | 4.6 | 8.6 | 0.5 | 13.7 | 5.4 | 3020 | 7.9 M |
| 96 | 6.4 | 17.2 | 0.9 | 24.5 | 4.6 | 1690 | 9.1 M |
| **192** | **9.2** | **34.3** | **3.3** | **46.8** | **4.4** | **885** | **9.5 M** |

实测首轮 42–48 s（含冷启），稳态 **~42 s/轮**，与表中 46.8 s（含 eval 摊入）吻合。
→ **取 g=192**：靠摊薄"每轮固定开销"再涨 20% 吞吐，且内存与每轮批大小都在安全区。
**三夜预算 ≈ 2650 轮 ≈ 28 M 样本更新。**

**提交前门槛（已完成）**：200 轮冒烟（≈2.6 h）确认了实测 s/iter、熵稳定性与对手池生效。

### 4.1 阶段 0：BC 预热 —— **默认不做**（★ 依据 10-12 夜跑的反证修正）

原来打算用 BC 预热加速起步，但 10-12 夜跑给出了明确反证：

- BC 产物 `bc_ac` 自身 **−0.529 显著劣于 s11**，接 1200 轮 RL 后仍是 **−0.530**（没救回来）；
- 验收脚本给了 `ok=true` 却漏掉行为退化：discard 一致率 100% → **92.79%（−7.21pp）**；
- 根因：`--freeze-old` 冻结旧参数，新通道引入的输入分布扰动无法被补偿；而 8e-6 的 RL lr 在 1200 轮内不足以修复（参数移动量 ~0.001 量级）。

**修订方案：**
1. **首发方案 A（推荐）**：跳过 BC，直接 RL。文献侧有强支持——DouZero 从零、Ataraxos 低算力超人类都无人类/教师数据。M1 有 10M 容量，冷启动的探索瓶颈比 0.77M 时小。
2. **备选方案 B**：若冷启动 200 轮冒烟测试出现熵坍缩或策略退化，再启用 BC，但必须**全网络解冻 + 分层 lr（头 10× 骨干）+ 预热后立刻切正常 lr**，且 BC 产物必须先在 200 副小规模对拍中达到**不劣于 s11** 才允许进入长训（这是本轮缺的那道门）。

### 4.2 阶段 1：自博弈 RL（A2C 骨架不动，只调四件事）

| 项 | 值 | 理由 |
|---|---|---|
| 算法 | 维持 REINFORCE+价值基线（现有 `update()`） | 2025 文献背书（§2）；管线零新风险 |
| lr | 1.2e-5 起步，看板动后 3e-6 精修 | 10M 网络初始梯度噪声大；沿用"自适应 KL 锚点"保护 |
| batch | **512**（实测 512/1024/2048 吞吐完全相同） | §4.0(c) |
| epochs-per-iter | **1** | 2 epoch 把 update 算力重复消耗在同一批数据上 |
| games-per-iter | **192**（实测最优；48→13.7s、96→24.5s、192→46.8s 含 eval） | §4.0(f)：靠摊薄每轮固定开销把 ms/样本从 5.4 压到 4.4 |
| threads / workers | **24 / 12** | §4.0(a)(b)：24 是实测最优点；12 workers 内存 ~6.6 GB，32 GB 下安全 |
| teacher-prob | **0.15 → 0.05** 两段退火 | 大网络容量大，教师占比过高会钉死在教师策略附近；0.15 起步只为稳定开局 |
| eval-every / eval-rounds | **20 / 40**（40 轮 = 65.8 s，摊入 3.3 s/轮） | §4.0(d)：比 60 轮省 1/3 时间，锚点配对 SE 已足够 |
| snapshot-every | **16**（默认 4） | 新增旋钮：快照池一变就要给 12 个 worker 全量重发 ≈350 MB（M1 是 s11 的 13 倍），间隔 16 把 IPC 摊薄 4 倍 |
| KL 锚点 / 熵看门狗 | kl-target 0.25、ent-floor 0.45、坍缩恢复流程 | 原样保留，这是两次救过训练的保险 |
| **anchor-warmup** | **200**（冷启动必设） | 新旋钮：M1 冷启动时 `ref_model` 是随机策略，锚上去等于往噪声拽，且自适应会把 kl_coef 顶到 3.0 |
| 温度 | 1.2 → 1.0（第二夜起） | 冷启动初期要探索；策略成型后降温度提稳定性 |
| 对手池 | 快照池 8 份 + **s11 全程坐庄 1 个座位** | 防遗忘 + 冷启动期提供稳定参考系（随机策略纯自博弈会退化） |

### 4.3 阶段 2：PTIE-critic 臂（M1-A vs M1-B 消融）

两臂同 seed 同预算，只差 oracle 分支启用。若 B 对 A 的配对净分差 CI 下界 > 0，保留 oracle 分支为标配。

## 5. 验收与晋升

1. **选点**：`score_checkpoints.py` 共用牌池复评全部 100 倍数快照（训练内 argmax 已被 winner's curse 坑过一次，不信训练内评测）；
2. **主门槛**：vs s11，1200 副配对净分差 **≥ +1.5 且 95% CI 下界 > 0**（远超常规换届门槛 +0.40，体现"远远超过"的目标）；
3. **交叉验证**：`roundrobin.py` 全组合循环赛 + `duel.py` 600 副 vs s11 独立复核（修正过 shift-seed 缺陷的口径）；
4. **多对手场**：vs `teacher:balanced` / `teacher:tenpai_rush` / s8（老风格）均不劣于 s11（防"只克制锚点"的过拟合）；
5. 换届流程照旧：备份 `dushan_master_prev_big_s11.pt` → 服务重启加载。

| 坑 | 事故 | 对策（写进训练脚本） |
|---|---|---|
| 机器睡眠 | C3 被冻结 22.2h、big_s6 损失 7.65h | 夜跑脚本内置 `SetThreadExecutionState(ES_CONTINUOUS\|ES_SYSTEM_REQUIRED)`，11.5h 预算闸门 |
| nohup 脱管 | s9 死于 iter 1171/1200、A4 空转 2h | **一律走托管后台任务，禁止 nohup** |
| 16GB 内存累积 | s4 崩于 840 轮、s5 崩于 3590 轮 | 进程池每 150 轮重建 + MemoryError 回收重试 ×3（M1 前向激活更大，**重建间隔改为 120 轮**） |
| BatchNorm train 污染 | 采集用 batch-of-1 统计决策 | 采集/评估前强制 `model.eval()`（断言写进 vcollect） |
| 快照 IPC | 每轮 450MB 占 70% 墙钟 | worker 快照缓存（snap_epoch 代数键）保留；M1 权重 ~40MB，缓存收益更大 |
| 热启动随机初始化 | C1：随机新通道挂上就掉 2.34 分 | v3 新通道/新参数**全部零初始化**，加载后输出逐位等于旧网 |
| 训练内 argmax 选点 | s7 评测分高于 s11 实际更弱 | 只信共用牌池复评（§5.1） |
| BC 数据形状 | "标 v2 实为 15 通道" | 数据体检第一步查张量形状 |
| **bf16/amp 误用** | 10-12 实测：M1 训练 b128 fp32=493ms，bf16=**23327ms（慢 47×）**；推理慢 20× | 本机仅 AVX2 无原生 bf16，训练脚本**显式断言禁用 autocast/amp**；torch 侧同步关闭 |
| **优化错方向** | 以为采集是瓶颈，去加 worker | 实测 update 占 70%、collect 只占 25% → 提速只能砍 `games-per-iter × epochs` |
| **BC 验收口径缺口** | BC 产物 −0.53 却 `ok=true`（只查"参数装上"+高置信翻转 ≤3%） | 新增门：BC 产物须在 ≥200 副配对小规模对拍中**不劣于锚点**才允许进长训 |
| torch 版本 | 2.9+ Windows OpenMP 加载失败 | 锁 torch 2.6.0+cpu |
| CPU 线程 | 24 线程实测最优，4 线程反而慢 17% | `--workers 12 --threads 24` 起步，首日 A/B 校准；duel/eval 用 8 线程隔离 |
| eval 阻塞 | 评测占 ~30% 墙钟 | M1 前向变慢后 eval-every 从 20 放宽到 **40**，靠 checkpoint 复评补选点 |
| rc≠0 误判 | 训练"跑完"实为中途失败 | 臂退出码非 0 一律重跑 |
| **stdout 空文件误判** | 10-12：`_night_bc_long.out` 0 字节，误以为训练没跑 | 脚本把日志写进自己的 `reports/plan_b_bc_long.log`；**判读看 summary/rescore JSON，不看外层重定向文件** |

## 7. 风险与后手

| 风险 | 概率 | 后手 |
|---|---|---|
| 实测 s/iter 高于投影（周期开销随轮数漂移） | 中 | 200 轮冒烟测试先测真值；超预算则 `games-per-iter` 降到 32 或退到变体 C/变体 E |
| 10M 网络 CPU 自博弈 12000 iter 不够 | 中 | 3 夜不够就延到 4 夜（每夜 ~11M 样本更新已与 s11 同量级）；或先前置 4M 版 M0 一夜验证"容量假说"再放大 |
| **冷启动不稳（无 BC 后）** | 中 | 200 轮冒烟；teacher-prob 从 0.15 起（比 s11 的 0.08 高）当稳定器；仍不稳再走方案 B |
| v3 新特征噪声拖累 | 低 | 包掩码逐包消融（P1 纪律），最差退回 31ch 纯容量版（9.6M） |
| 熵坍缩更猛烈（大网更自信） | 中 | 看门狗已有两级熔断；epochs 锁定 1 先手 |
| PTIE oracle 泄漏 | 低 | oracle 只进价值头且部署置零，策略头路径不变 |
