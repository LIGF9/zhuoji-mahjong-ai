## 1. 算力实测：不同规模网络要多久

当前机器为 **Intel 11 代 Tiger Lake，4 核 8 线程**（`torch 2.6.0+cpu`，
`threads=8`，每轮 96 局自对弈 ≈ 4300 样本、batch 512、2 个 epoch）。
下表是 `scripts/bench_scale.py` 的实测值：

| 网络配置 (C/B/H) | 参数量 | 单 batch | 更新/轮 | 含采集/轮 |
|---|---|---|---|---|
| 64/8/320（当前 big 网） | 0.77M | 530 ms | 9.5 s | 11.5 s |
| 96/12/448 | 2.31M | 2.11 s | 38.0 s | 40.0 s |
| 128/16/512 | 5.14M | 2.81 s | 50.6 s | 52.6 s |
| **160/20/512（≈10M）** | **9.67M** | **5.34 s** | **96.1 s** | **98.1 s** |
| 192/24/576（15M 级） | 16.50M | 8.63 s | 155.3 s | 157.3 s |

> 实际训练日志交叉验证：big 网每轮 `collect=1.8~2.4s`、`total≈9.6s`，
> 与基准表的量级一致（基准略偏保守）。

**两个读数：**

1. **cost 基本随参数量线性增长。** 0.77M → 9.67M 是 12.6 倍参数、10.1 倍耗时。
   说明小网络下 CPU 的 BLAS 利用率已经打满，靠加宽加深不会"免费"。
2. **5.1M 是性价比拐点。** 96/12/448 → 128/16/512：参数翻 2.2 倍，耗时只涨 33%；
   再往上到 10M 才开始明显地线性付费。如果要在 CPU 上加参数，先试 128/16/512。

### 14700K 预期（按 3.0–4.5× 估算）

加速来源：4C8T → 8P+12E（20 核 28 线程）、全核频率 3.x → 5.3 GHz、DDR4 → DDR5。
笔记本的持续功耗墙（15–28 W）会让旧机器的长时间全核频率进一步掉档，所以实际
加速比可能比纸面更大。保守按 **3.0–4.5×** 取：

| 网络 | 14700K 估计 /轮 | 24 h 可跑轮数 | 10 代 × 1000 轮 |
|---|---|---|---|
| 0.77M | 2.5–4 s | 21000–34000 | < 半天 |
| 2.3M | 9–14 s | 6000–9500 | ≈ 1 天 |
| 5.1M | 12–19 s | 4500–7200 | 1.5–2 天 |
| **9.7M** | **17–35 s** | **2500–5000** | **3–4 天** |
| 16.5M | 35–52 s | 1700–2500 | 4–6 天 |

**所以算力不是挡路的。** 3–4 天就能把 10M 跑完 10 代。真正的问题是：跑完了也
未必变强——见 §4。

> 迁移后第一件事：在新机器上跑 `python scripts/bench_scale.py --threads 20
> --json reports/bench_14700k.json`，与上表对比得到**真实**加速比（别用估算）。

#### 2.0.1 若 `github.com:443` 不通（本机实测就中招了）

某些网络会**单独屏蔽 `github.com:443`**，症状很隐蔽：`ping github.com` 通（ICMP 正常），
`api.github.com` 也能访问，**只有 HTTPS clone/push 卡死或超时**。本机（开发机）2026-10-09 实测：

| 目标 | 结果 |
|---|---|
| `github.com:443` | ❌ TCP 超时 |
| `api.github.com:443` / `github.com:22` / `ssh.github.com:443` | ✅ |
| `codeload` / `raw` / `objects.githubusercontent.com:443` | ✅ |

**判断方法**（别只靠 ping）：

```bash
ssh -T git@github.com          # 通 → SSH 通道可用
git ls-remote https://github.com/LIGF9/zhuoji-mahjong-ai.git   # 卡住 → 443 被屏蔽
```

**绕法：改走 SSH。** 在新机器上生成一把自己的密钥，用 token 注册成**仓库级部署密钥**
（只授权这一个仓库，不碰账号其它仓库）：

```bash
ssh-keygen -t ed25519 -N "" -f ~/.ssh/zhuoji_deploy
# 用 token 调 API 注册公钥（api.github.com 通常不受影响）
python - <<'PY'
import json, urllib.request, os
tok = open("token.txt").read().strip()
pub = open(os.path.expanduser("~/.ssh/zhuoji_deploy.pub")).read().strip()
req = urllib.request.Request(
    "https://api.github.com/repos/LIGF9/zhuoji-mahjong-ai/keys",
    data=json.dumps({"title": "new-machine", "key": pub, "read_only": False}).encode(),
    method="POST")
req.add_header("Authorization", "Bearer " + tok)
req.add_header("User-Agent", "bootstrap")
print(urllib.request.urlopen(req, timeout=25).status)   # 201 = 成功
PY

git clone git@github.com:LIGF9/zhuoji-mahjong-ai.git zhuoji-mahjong
cd zhuoji-mahjong
git config core.sshCommand "ssh -i ~/.ssh/zhuoji_deploy -o IdentitiesOnly=yes"
```

本开发机已经这么做过（私钥 `~/.ssh/zhuoji_deploy`，仓库级 `core.sshCommand` 已配好），
所以在这台机器上**裸 `git push` 就能用**，不需要 token。
发布脚本也内置了自动回退：

```bash
python scripts/publish_to_github.py --token-file <token 文件> \
    --repo zhuoji-mahjong-ai --public --skip-commit      # --via auto 会探测 443 后自动走 SSH
```

#### C3 是什么、为什么不在包里

`C3` 是判定「P1b 掉分究竟是迁移扰动还是特征有害」的**决定性单变量对照**
（零初始化 + 400 轮，与 `p_abc` 只差 `--new-param-init` 一个变量）。打包时它
训练到 `iter 229/400`，本机仍在跑，约 **13:24 训练完 + 65 min 复评 → 约 15:00 出判读**。

**两条路，任选其一**：

* **A. 新机重跑（推荐，最快）** —— 14700K 上约 25–35 分钟。命令（与旧机器逐字一致）：
  ```bash
  python scripts/selfplay.py --init models/dushan_big_s11.pt \
      --out models/dushan_b2c_p_abc_zero.pt \
      --history reports/rl_history_b2c_p_abc_zero.json \
      --iters 400 --games-per-iter 96 --batch 512 --lr 8.0e-6 --temperature 0.95 \
      --teacher-prob 0.08 --threads 16 --vectorized --workers 8 \
      --eval-every 10 --eval-rounds 40 \
      --select guard --select-metric vs_anchor --eval-anchor dushan_big_s11 \
      --save-every 50 --snapshot-pool dushan_big_s3,dushan_big_s7,dushan_big_s11 \
      --encoder v2 --encoder-packs abc --spatial-head off --new-param-init zero \
      --seed 20270 --rules dushan
  ```
  跑完执行复评（6 检查点 × 1200 副共用牌池）：
  ```bash
  python scripts/score_checkpoints.py \
      --ckpts dushan_b2c_p_abc_zero,dushan_b2_p_abc,dushan_b2_p_none,dushan_b2_sp_off,_diag_c1_v2warm,dushan_big_s11 \
      --ref "net:dushan_big_s11|teacher:balanced|teacher:tenpai_rush" \
      --deals 1200 --threads 8 --anchor dushan_big_s11 --no-per-deal \
  ```

  无显著差异且都显著负 → H2（特征本身有害）。

## 3. 几个坑（已踩过，别再踩）

1. **时间戳/环境变量**：值班链 `shift_chain_*.py` 用 `ctypes.windll` 防休眠，
   仅 Windows 有效。
2. **Windows 路径**：脚本内一律用 `pathlib` 和 `/`，新机器盘符不同不影响。
3. **curl 代理**：本机测网页接口时若走代理会失败，用 `curl --noproxy '*'`。
4. **值班链对位赛传参**：`duel.py --a/--b` 收的是**裸文件名**（内部拼
   `models/{stem}.pt`），别传完整路径，否则会变成 `models/models/xxx.pt.pt`。
5. **后台任务会被连带杀**：7 小时值班链如果挂在一个会被回收的父进程下，可能
   整棵进程树被带走（s9 就死在 iter 1171/1200）。**别用 `nohup ... &` 脱离式启动**
   —— 父 shell 一退出就被连带终止（A4 因此白丢 2 h）。用工具的托管后台。
6. **系统空闲睡眠会「冻结」长跑，且症状极隐蔽**：进程**还在**（`tasklist` 看得见），
   但计算停止，日志 `total`（墙钟）继续累加、`iter` 编号却不前进。C3 曾因此被冻结
   **22.2 h**（`total` 从 328s 跳到 80196s，iter 24→25 连续）。
   判别三招：① 看 `total` 是否有突兀跳跃；② `psutil.boot_time()` 未重启；
   ③ 恢复后速率正常 → 不是崩溃。**对策：长跑前先起 `python scripts/keep_awake.py`**
   （`SetThreadExecutionState` 阻止空闲睡眠，目标进程退出后自动清除标记）。

## 4. 只换机器够不够？——路线判断

**不够，而且换机不是当前的主要杠杆。**

P0 阶段（评测与选点重建）已经给出了硬证据：

- 训练内「评测均分」与真实强度的 **Spearman 秩相关 ρ ≈ 0.14 / 0.007**，
  即**几乎无信息量**；
- 换个对手场重算，冠军就换人（场 A 冠军 s9、场 B 冠军 s4）——两场之间 ρ=0.615；
- **s1–s11 十几代、累计上万轮，绝大多数两两对比统计上不可区分**；唯一稳定结论
  是小网明显更弱。

也就是说：**在 0.77M 规模、当前表征下，继续堆训练量已经不再产生可测量的增益。**
这时候把网络放大到 10M、再堆十几天算力，最可能的结果是把这条"打平曲线"整体
平移——参数量不是此刻的瓶颈。

10M 网络的额外风险：**它需要多得多的数据才能被喂饱**。当前每轮 96 局、一代
1000 轮 ≈ 9.6 万局自对弈；AlphaZero 类参数规模通常对应百万局级经验，而且要靠
对手池和搜索带来多样性。纯自对弈放大网络，很容易训出一个"参数很多但只会重复
自己毛病"的模型。

### 建议的顺序

| 阶段 | 内容 | 算力需求 | 为什么先做 |
|---|---|---|---|
| **P1** | **表征升级**：牌河时序（最近几巡的出牌/摸牌）、巡目与剩余牌数、危险度、番型潜力、match 分数情境 | 低（0.77–2.3M 即可验证） | 改变"能看到什么信息"，是容量之外的独立维度。P0 标尺已能分辨增益。 |
| **P2** | **训练方法**：GRP 降方差 + Oracle 引导 + λ-return | 中 | 直接对着"梯度噪声大、优势估计弱"下手 |
| **P3** | **放大规模**：5.1M → 10M，同时把 `--games-per-iter` 提到 300–500，配 P0 标尺做长跑 | 高（这时才需要 14700K） | 只有 P1/P2 被证实有效，放大才有意义 |

**换机应该和 P1 一起做**：14700K 上 0.77–2.3M 网络只要 2.5–14 s/轮，一天能跑
几千轮，足够把 P1 的表征消融实验快速迭代完。等 P1 确认有增益（P0 标尺上显著），
再放大网络。

### 关于"职业水平"

目前**没有任何可验证的职业级参照**。现有对手只有若干启发式教师，最强锚点是
s7/s11 自己。在把 10M 训出来之前，建议先解决"怎么证明它到职业水平了"：
接入公开麻将 AI 复现（如 Tenhou 数据训练的策略网）或人类高质量牌谱作为锚点，
否则 10M 训完仍然只能得到"它和自己差不多"这种结论——就像 P0 发现的那样。

### 顺带一提：显卡

你选了纯 CPU，这个前提我保留。但值得知道代价：一张 16 GB 显存的卡
（如 4060 Ti 16G）能让 10M 网络全 batch 上 GPU，每轮降到 **1 s 以内**，
一天跑几万轮——那是"小时级出多代"和"天级出一代"的区别。如果哪天想真正把
10M + 百万局级自对弈做实，这才是最短路径。CPU 路线能做到"跑得起来、看得见
趋势"，但想逼近职业水平，算力迟早会变成第二瓶颈。
