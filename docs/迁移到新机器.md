# 迁移到新机器（Intel 14700K / 无独显）

本文回答三件事：**换机能不能训出 10M 的职业级网络**、**怎么把项目搬过去**、
**换机后要先做什么**。附当前机器的实测吞吐基准，换机后可逐项对比。

---

## 0. 结论先行

| 问题 | 回答 |
|---|---|
| 14700K 无独显能训 10M 网络吗？ | **能，算力够。** 10M 网络估计 17–35 s/轮，跑满一天约 2500–5000 轮，10 代 × 1000 轮 ≈ 3–4 天。 |
| 换机就能到职业水平吗？ | **不能。** 换机解决的是"迭代太慢"，不解决"梯度方向"。P0 已证明当前训练量下 s1–s11 大多无法区分——瓶颈在**表征**和**训练方法**，不在算力。 |
| 登录同账号续聊就行吗？ | **对话能续，文件不会自动过去。** 会话历史在云端，但工作目录是本机磁盘上的，必须手工搬。 |
| 你会自动帮我同步吗？ | **不会。** 我运行在这台机器上，没有跨设备同步通道。已备好一键打包 + 一键修复脚本（见 §2）。 |

## 1. 算力实测：不同规模网络要多久

当前机器为 **Intel 11 代 Tiger Lake，4 核 8 线程**（`torch 2.6.0+cpu`，
`threads=8`，每轮 96 局自对弈 ≈ 4300 样本、batch 512、2 个 epoch）。
下表是 `scripts/bench_scale.py` 的实测值：

| 网络配置 (C/B/H) | 参数量 | 单 batch | 更新/轮 | 含采集/轮 |
|---|---|---|---|---|
| 64/8/320（当前 big 网） | 0.77M | 530 ms | 9.5 s | 11.5 s |
| 96/12/448 | 2.31M | 2.11 s | 38.0 s | 40.0 s |
| 128/16/512 | 5.14M | 2.81 s | 50.6 s | 52.6 s |
| **160/20/512（≈10M）** | **9.67M** | **5.34 s** | **96.1 s** | **98.1 s** |
| 192/24/576（15M 级） | 16.50M | 8.63 s | 155.3 s | 157.3 s |

> 实际训练日志交叉验证：big 网每轮 `collect=1.8~2.4s`、`total≈9.6s`，
> 与基准表的量级一致（基准略偏保守）。

**两个读数：**

1. **cost 基本随参数量线性增长。** 0.77M → 9.67M 是 12.6 倍参数、10.1 倍耗时。
   说明小网络下 CPU 的 BLAS 利用率已经打满，靠加宽加深不会"免费"。
2. **5.1M 是性价比拐点。** 96/12/448 → 128/16/512：参数翻 2.2 倍，耗时只涨 33%；
   再往上到 10M 才开始明显地线性付费。如果要在 CPU 上加参数，先试 128/16/512。

### 14700K 预期（按 3.0–4.5× 估算）

加速来源：4C8T → 8P+12E（20 核 28 线程）、全核频率 3.x → 5.3 GHz、DDR4 → DDR5。
笔记本的持续功耗墙（15–28 W）会让旧机器的长时间全核频率进一步掉档，所以实际
加速比可能比纸面更大。保守按 **3.0–4.5×** 取：

| 网络 | 14700K 估计 /轮 | 24 h 可跑轮数 | 10 代 × 1000 轮 |
|---|---|---|---|
| 0.77M | 2.5–4 s | 21000–34000 | < 半天 |
| 2.3M | 9–14 s | 6000–9500 | ≈ 1 天 |
| 5.1M | 12–19 s | 4500–7200 | 1.5–2 天 |
| **9.7M** | **17–35 s** | **2500–5000** | **3–4 天** |
| 16.5M | 35–52 s | 1700–2500 | 4–6 天 |

**所以算力不是挡路的。** 3–4 天就能把 10M 跑完 10 代。真正的问题是：跑完了也
未必变强——见 §4。

> 迁移后第一件事：在新机器上跑 `python scripts/bench_scale.py --threads 20
> --json reports/bench_14700k.json`，与上表对比得到**真实**加速比（别用估算）。

## 2. 怎么把项目搬过去

### 2.0 最快路径：直接从 GitHub clone（推荐）

项目已发布到 GitHub（**公开仓库**）：

```
https://github.com/LIGF9/zhuoji-mahjong-ai
```

新机器上一条命令搞定，不用 U 盘、不用打包：

```bash
git clone https://github.com/LIGF9/zhuoji-mahjong-ai.git zhuoji-mahjong
cd zhuoji-mahjong
```

**仓库只含「跑得起来 + 训得出来」的复现必要文件（约 16 MB / 121 个文件）**：

| 入库 | 内容 |
|---|---|
| ✅ 代码 | `zhuoji/`（引擎）、`scripts/`（训练/评测）、`tests/`、`web/*.py` |
| ✅ 权重 | `models/` 仅 4 个：`dushan_master.pt`（成品大师）、`dushan_big_s11.pt`（当前代）、`dushan_big_s7.pt`（对照基线）、`bc.pt`（BC 初始策略） |
| ✅ 网页 | `web/static/dushan.html` 等页面 + 游戏视觉资源（`tiles/` `sprites/` `table/` `avatar/`） |
| ✅ 文档 | `docs/`、`README.md`、`requirements.txt`、`reports/*.md`（结论文档） |

**未入库（都可再生成，或在旧机器上另存）**：

| 排除项 | 体积 | 恢复办法 |
|---|---|---|
| `data/`（BC 数据集 + 分片） | ~99 MB | `python scripts/gen_bc_data.py --games 4000` |
| `reports/` 非 md（日志/历史 json/快照） | ~36 MB | 从旧机器拷，或删除 `.gitignore` 里 `reports/*` 两行 |

（或从旧机器拷贝）。只想**对局/评测**的话，clone 完即可用（权重齐全）。

只有以下情况才需要走 §2.2–§2.3 的离线打包：新机器访问 GitHub 不稳定/被限速，
或本地又产生了**未推送**的新权重/新报告。

## 3. 几个坑（已踩过，别再踩）

1. **时间戳/环境变量**：值班链 `shift_chain_*.py` 用 `ctypes.windll` 防休眠，
   仅 Windows 有效。
2. **Windows 路径**：脚本内一律用 `pathlib` 和 `/`，新机器盘符不同不影响。
3. **curl 代理**：本机测网页接口时若走代理会失败，用 `curl --noproxy '*'`。
4. **值班链对位赛传参**：`duel.py --a/--b` 收的是**裸文件名**（内部拼
   `models/{stem}.pt`），别传完整路径，否则会变成 `models/models/xxx.pt.pt`。
5. **后台任务会被连带杀**：7 小时值班链如果挂在一个会被回收的父进程下，可能
   整棵进程树被带走（s9 就死在 iter 1171/1200）。长跑任务建议独立窗口运行。

## 4. 只换机器够不够？——路线判断

**不够，而且换机不是当前的主要杠杆。**

P0 阶段（评测与选点重建）已经给出了硬证据：

- 训练内「评测均分」与真实强度的 **Spearman 秩相关 ρ ≈ 0.14 / 0.007**，
  即**几乎无信息量**；
- 换个对手场重算，冠军就换人（场 A 冠军 s9、场 B 冠军 s4）——两场之间 ρ=0.615；
- **s1–s11 十几代、累计上万轮，绝大多数两两对比统计上不可区分**；唯一稳定结论
  是小网明显更弱。

也就是说：**在 0.77M 规模、当前表征下，继续堆训练量已经不再产生可测量的增益。**
这时候把网络放大到 10M、再堆十几天算力，最可能的结果是把这条"打平曲线"整体
平移——参数量不是此刻的瓶颈。

10M 网络的额外风险：**它需要多得多的数据才能被喂饱**。当前每轮 96 局、一代
1000 轮 ≈ 9.6 万局自对弈；AlphaZero 类参数规模通常对应百万局级经验，而且要靠
对手池和搜索带来多样性。纯自对弈放大网络，很容易训出一个"参数很多但只会重复
自己毛病"的模型。

### 建议的顺序

| 阶段 | 内容 | 算力需求 | 为什么先做 |
|---|---|---|---|
| **P1** | **表征升级**：牌河时序（最近几巡的出牌/摸牌）、巡目与剩余牌数、危险度、番型潜力、match 分数情境 | 低（0.77–2.3M 即可验证） | 改变"能看到什么信息"，是容量之外的独立维度。P0 标尺已能分辨增益。 |
| **P2** | **训练方法**：GRP 降方差 + Oracle 引导 + λ-return | 中 | 直接对着"梯度噪声大、优势估计弱"下手 |
| **P3** | **放大规模**：5.1M → 10M，同时把 `--games-per-iter` 提到 300–500，配 P0 标尺做长跑 | 高（这时才需要 14700K） | 只有 P1/P2 被证实有效，放大才有意义 |

**换机应该和 P1 一起做**：14700K 上 0.77–2.3M 网络只要 2.5–14 s/轮，一天能跑
几千轮，足够把 P1 的表征消融实验快速迭代完。等 P1 确认有增益（P0 标尺上显著），
再放大网络。

### 关于"职业水平"

目前**没有任何可验证的职业级参照**。现有对手只有若干启发式教师，最强锚点是
s7/s11 自己。在把 10M 训出来之前，建议先解决"怎么证明它到职业水平了"：
接入公开麻将 AI 复现（如 Tenhou 数据训练的策略网）或人类高质量牌谱作为锚点，
否则 10M 训完仍然只能得到"它和自己差不多"这种结论——就像 P0 发现的那样。

### 顺带一提：显卡

你选了纯 CPU，这个前提我保留。但值得知道代价：一张 16 GB 显存的卡
（如 4060 Ti 16G）能让 10M 网络全 batch 上 GPU，每轮降到 **1 s 以内**，
一天跑几万轮——那是"小时级出多代"和"天级出一代"的区别。如果哪天想真正把
10M + 百万局级自对弈做实，这才是最短路径。CPU 路线能做到"跑得起来、看得见
趋势"，但想逼近职业水平，算力迟早会变成第二瓶颈。
