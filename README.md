一个从零构建的**贵阳捉鸡麻将** AI：自研规则引擎 → 启发式教师 → 行为克隆 →
自我对弈强化 → 复式评测。不依赖任何现成对局数据（原因见下）。

## 0. 先说数据这件事

任务起点给的是 Botzone 的比赛页 `gamecontest2026a_cn.html`。核实结论：

| 核实项 | 结果 |
|---|---|
| 该页面是什么比赛 | 第六届国际麻将人工智能比赛（IJCAI 2026），规则是**国标麻将（MCR）**，不是捉鸡 |
| 国标 vs 捉鸡差异 | 国标 144 张含字牌花牌、**可吃**、8 番起胡、81 种番型；捉鸡 108 张无字牌、**不能吃**、豆（杠）当点胡通行证、捉鸡/冲锋鸡/责任鸡算分。**规则空间几乎不重叠** |
| 官方"强 AI 对局数据"（北大网盘） | AnyShare 单页应用，需交互登录才能拿直链，脚本抓不到 |
| Botzone 全站数据下载站 `extra.botzone.org.cn/matchpacks/` | 页面能开，但**打包文件所在域当前 502** |
| Botzone 上有没有"捉鸡麻将"这个游戏 | **没有**。全站游戏列表（865KB）里不存在该条目，因此平台内也无捉鸡对局可爬 |
| 可用的替代数据 | `hf-mirror.com` 上有国标麻将对局数据（9.8 万局）+ 决赛强 AI 数据 + 预训练权重 |

**结论：捉鸡没有公开对局数据，必须自产。** 本项目采用：

1. 自研规则引擎精确实现捉鸡规则；
2. 用 6 种风格的启发式教师跑出大规模对局做**行为克隆**；
3. 再用**自我对弈强化学习**超越教师。

> 若日后想加"国标迁移预训练"，可把 HF 镜像上的国标数据按"不含字牌的状态"筛出来
> 做辅助任务，但跨规则迁移的收益不确定，本项目未启用。

## 1. 规则档（贵阳捉鸡）

各地捉鸡规则差异不小，本项目把**所有分歧点**收进 `RulesConfig`，默认取通用口径。

**基础**
- 108 张：万 / 条 / 筒 各 1–9，每种 4 张。无字牌、无花牌。
- 4 人；庄家 14 张，闲家 13 张；首局随机定庄，之后胡牌者接庄。
- 可摸 / 碰 / 杠 / 胡，**不可吃**。

**豆（杠）= 点胡通行证**
- 无豆时，平胡**只能自摸**；平胡以上牌型（番 ≥ 5）可无豆点胡。
- 闷豆（暗杠）其他三家各付 `2`；爬坡豆（补杠）各付 `3`；点豆（明杠）`1` 番，
  默认**由杠者付给被点者**（百科口径，可用 `dian_dou_payer="discarder"` 反过来）。
- 「得豆必须听牌才生效」：整局从未进入听牌的玩家，其豆不计分（`dou_requires_tenpai`）。

**鸡**
- 幺鸡（1 条）恒为鸡；胡牌后翻牌墙第一张未摸牌，其"点数 +1 同花色"也是鸡
  （翻 9 筒 → 1 筒）；翻到 9 条时幺鸡升为**金鸡**，每张 `2` 番。
- 每持 1 张鸡，其他三家各付对应番数。
- **冲锋鸡**：本局第一个打出的幺鸡，结算时倍率 ×2（金鸡时值为 4）。
- **责任鸡**：那张幺鸡被碰走，打出者比其他人多付 `1` 番。
- 满堂鸡（四家都有鸡则翻倍）为部分地区玩法，默认关闭。

**番型**

| 牌型 | 番 | | 牌型 | 番 |
|---|---|---|---|---|
| 平胡 | 1 | | 清一色 | 10 |
| 大对子 | 5 | | 清大对 | 15 |
| 七对 | 7 | | 清七对 | 17 |
| 龙七对 | 10 | | 青龙背 | 20 |

**结算**
- 底分 ×（牌型番 + 豆番 + 鸡番）；坐庄胡牌 +1 番，连庄按连庄盘数加。
- 自摸三家付；点胡点炮者单独付；抢杠算自摸且被抢杠者包三家。
- **全烧**：杠后打出的第一张牌点炮，该点炮者的豆、鸡全部作废。
- **黄庄查叫**：牌摸完无人胡 → 亮牌查叫；四家全叫或全不叫算平局；部分叫则未叫者
  按叫牌者番值赔付。**黄庄时豆、鸡一律不算分。**

**已知分歧点**（已在 `RulesConfig` 中参数化，默认值取自百度百科口径）
- 点豆赔付方向：百科为「杠者付给被点者」，部分牌桌相反。
- 冲锋鸡价值：百科为「加倍」（2 番），部分平台为 3 番甚至 6 番。
- 责任鸡：百科 `+1` 番，部分口径 `+2` 番。
- 鸡的统计范围：默认「手牌 + 副露」，可切到「含自己牌河」（满堂鸡口径）。

## 3. 状态编码

**相对视角**：永远把当前决策者放在座位 0（下家 1 / 对家 2 / 上家 3），
一次训练即可覆盖四个座位。

**牌面特征 `(15, 27)`**，27 = 3 花色 × 9 点数：

| 通道 | 含义 |
|---|---|
| 0–3 | 自己手牌计数 ≥1 / ≥2 / ≥3 / =4 |
| 4 | 自己手牌计数 / 4 |
| 5–8 | 四家牌河计数 / 4（相对座位） |
| 9–12 | 四家副露计数 / 4 |
| 13 | 该牌已现张数 / 4 |
| 14 | 该牌未现张数 / 4 |

**全局标量 `(70,)`**：牌墙剩余、进度、庄家 one-hot、连庄数、四家的豆数 / 副露数 /
牌河数 / 是否曾听牌、自己是否持有豆、听牌张数、幺鸡存量、冲锋鸡与责任鸡归属、
当前阶段 one-hot，以及上一张打出的牌的 one-hot + 出牌者。

**三个动作头**（与引擎的三个决策点一一对应，各自带合法动作掩码）：

| 头 | 维度 | 含义 |
|---|---|---|
| `discard` | 28 | 0–26 打某张牌，27 = 自摸胡 |
| `self_kong` | 28 | 0–26 闷豆/爬坡豆某张牌，27 = 过 |
| `respond` | 4 | 过 / 碰 / 点豆 / 胡 |

## 4. 训练流程

### 4.1 一键跑通

```bash
python scripts/run_all.py --quick   # 几分钟的小规模全链路冒烟（自检→数据→BC→RL→评测→报告）
python scripts/run_all.py           # 默认的小规模正式跑
```

`run_all.py` 按顺序执行：自检 → 生成数据 → 行为克隆 → 自我对弈强化 → 复式评测
→ 样例对局 → HTML 报告，任何一步非零退出就立刻停下。常用开关：

| 开关 | 作用 |
|---|---|
| `--quick` | 每步都用极小规模，只为验证链路通 |
| `--regen-data` | 即使 `data/bc_data.npz` 已存在也重新生成 |
| `--no-rl` | 跳过自我对弈，只到 BC 为止 |

### 4.2 分步执行

```bash
# 1) 生成行为克隆数据（6 进程，8000 局 → 数十万样本）
python scripts/gen_bc_data.py --games 8000 --workers 6

# 2) 行为克隆
python scripts/train_bc.py --epochs 10 --channels 32 --blocks 3

# 3) 自我对弈强化
python scripts/selfplay.py --iters 30 --games-per-iter 64

# 4) 复式对战评测（跑两份，报告里并排对比"强化后 / 强化前"两代模型）
python scripts/arena.py --model models/rl.pt --baseline models/bc.pt \
    --rounds 240 --seed 777 --out reports/arena.json
python scripts/arena.py --model models/bc.pt \
    --rounds 240 --seed 777 --out reports/arena_bc.json

# 5) 逐副牌配对比较（这一步才分得出 RL 和 BC 谁强）
python scripts/compare_arena.py --a reports/arena.json --b reports/arena_bc.json

# 6) 导出样例对局（含模型在每个决策点的动作概率）
python scripts/make_sample_game.py --model models/rl.pt

# 7) 生成 HTML 报告
python scripts/make_report.py
```

产物：`models/bc.pt`、`models/rl.pt`、`reports/bc_history.json`、
`reports/rl_history.json`、`reports/arena.json`、`reports/arena_bc.json`、
`reports/compare.json`、`reports/sample_game.json`、`reports/report.html`。

`arena.py --baseline` 会把另一个模型塞进对手池，于是同一张表里既能看
"我方 vs 教师"，也能看"新模型 vs 旧模型"的正面对撞。把上一代模型当对手，
比只看对启发式教师的胜率更能说明强化到底有没有长进。

**两次评测必须用同一个 `--seed`**：对手种子由 `arena.det_seed()` 从对手名确定性推出
（早先版本用 `torch.randint` 现场抽，导致两份评测的对手根本不是同一批实例，
配对分析直接失效）。同 seed + 同 rounds 下，两份评测吃的是完全相同的牌，
`compare_arena.py` 才能逐副做差把牌运消掉。

### 4.3 依赖

```bash
pip install -r requirements.txt
```

本项目在一台 **纯 CPU** 机器上开发与训练（Intel i5-11320H / 8 线程 / 16GB），
依赖为 `torch==2.6.0+cpu` + `numpy` + `matplotlib`（matplotlib 只用于可选出图，
HTML 报告里的曲线是手写内联 SVG，不依赖它）。

### 4.4 训练目标
- BC：三个头的掩码交叉熵（按头样本量加权）+ 终局得分回归 + 熵正则；
  响应头里的"过"动作按比例下采样以缓解类别不平衡。
- RL：`A(s,a) = 终局得分 - V(s)`，
  `L = -E[log π · A.detach()] + λ_v·SmoothL1(V,R) - λ_e·H(π) + λ_k·KL(π‖π_BC)`。
  终局得分除以 `reward_scale` 归一；优势做批内标准化。

**为什么用 REINFORCE 而不是 PPO**：一局 60+ 决策点但回报只在终局出现一次，
优势用价值头当基线已足够；在"每轮重采样、只更新 1–2 个 epoch"的设定下 PPO 的
clip 收益有限，反而增加实现风险。

## 5. 评测

`play_duplicate` 用**复式**方式：同一副起手牌让每个 Agent 轮换坐四个座位各打一次，
消掉牌运方差，只比策略差异。指标：平均得分、胡牌率、自摸率、点炮率、黄庄率、
胡牌平均番数。

返回值里带 `avg_score_se`：**同一副牌的四次轮换被压成一个观测**（`deals` 就是副牌数），
标准误按副牌数算。不这么做的话，同副牌内的相关性会把误差棒算小到离谱，
容易把牌运噪声当成功力提升。评测表里对被测模型会把标准误一并打出来。

### 5.1 别只看胜率：一次真实的翻车记录

第一版 RL 配置 `kl_coef=0.02, lr=3e-4` 跑了 80 轮。训练日志里评测平均分从
-0.80 涨到 -0.24，看着像在收敛。

但把两代模型放到同一张桌上对撞（`arena.py --baseline models/bc.pt`），
RL 一侧是 -1.17、BC 一侧 +0.39——**看着"在涨"的那版其实被 BC 反杀**。

真正定案的证据不是胜负，而是训练曲线本身：

| 指标 | 未锚定 | 加锚定 |
|---|---|---|
| 策略熵 | 1.44 → **0.07**（塌成近乎确定性） | 稳在 1.27–1.34 |
| KL(π‖π_BC) | → **2.4 nats**（彻底脱离教师分布） | 稳在 0.03 |

熵崩 + KL 暴涨说明策略已经跑飞：价值头在拟合自我对弈的回报，策略于是学会了
「稳定地打一套自洽但不强的牌」。修正办法是把 `kl_coef` 从 0.02 提到 0.8、
`lr` 从 3e-4 降到 5e-5、`teacher_prob` 从 0.5 降到 0.15，训练过程立刻受控。

**教训有两条**：一是自我对弈里的评测集如果和训练分布同源，指标会跟着一起漂，
必须留一个静态的、训练外的锚；二是**别拿胜率当唯一证据**——捉鸡单局方差极大
（冲锋鸡、责任鸡、黄庄查叫都是高波动结算项），几百副牌只能分辨量级很大的差异。
本套件在评测里直接给出标准误和 `t` 值，`|t| < 2` 的对比一律读作"暂无结论"。

### 5.2 配对比较：先让两个模型坐同一把椅子

标准误 0.15 意味着"两份独立评测的均值相减"只能分辨 0.3 分以上的差距，
而两代模型的真实差距往往就在 0.1~0.2 —— 直接比均值等于白跑。

`compare_arena.py` 的做法是把复式思想再往前推一步：

| | 普通复式（`arena.py`） | 配对比较（`compare_arena.py`） |
|---|---|---|
| 同一副牌 | 四个 Agent 轮换座位各打一次 | ✅ 还要让两个被测模型吃**同一批牌** |
| 对手 | 随机抽种子 | **确定性种子**（同样的对手实例） |
| 噪声 | 牌运被平均掉一部分 | 牌运**逐副做差直接消掉** |

有了逐副牌的得分记录（`per_deal`，同一副牌的四次轮换压成一个观测），
就能算 `d_r = score_RL(r) − score_BC(r)` 的均值与标准误。本项目实测：

| | 未配对 | 配对后 |
|---|---|---|
| RL − BC | 需要上千副牌才测得出 | **+0.115 ± 0.055 分/局（t = +2.10）** |
| 差值方差 | — | 相对独立比较**压缩 35%~59%** |

7 组对手里 6 组差值为正、方向一致。**同算力下这是最划算的一步精度提升。**

**实现注意**：跨模型配对的前提是"两份评测的对手是同一批实例"，
所以 `arena.py` 里的对手种子必须由对手名确定性推出，不能用现场随机数生成。

### 5.3 别用训练内评测选点（它分辨不出代际差异）

训练里默认用「对固定三位启发式教师、`--eval-rounds` 副（默认 40 副 = 160 局）」
的评测均分做 `argmax` 选点：**只有超过历史最佳才写 `--out`**。这个做法有问题：

| | 数值 |
|---|---|
| 训练内评测（160 局）的 `avg_score_se` | ≈ **0.97** → 95% CI ≈ **±1.9 分** |
| 真实代际提升（S11 vs S7，2400 副对位赛） | **+0.319 ± 0.288 分** |

指标的噪声比它要分辨的信号大 6 倍。于是"选评测最高分"等于在噪声里抽签，
还会把恰好抽高的那一刻当成最好（winner's curse）。实测证据：
`s7` 的评测分 8.60 高于 `s11` 的 7.231，但 `s11` 才是更强的那一代。

要做到"测出 0.3 分的差距"，约需 **2200 副**牌的对位赛
（`(1.96 × 7.2 / 0.3)² ≈ 2213`，与 2400 副实测 CI ±0.288 相符）——
训练内不可能每 N 轮做一次。

因此现在改成两条腿：

1. **训练内不追高**：`selfplay.py --select {max,last,guard}`。
   `guard`（推荐）= 采用最后一轮，只在「最近 3 次评测的均值 + 2×SE 仍低于全程中位数」
   这种**超出噪声的实质退化**时才回退到历史最佳——不追噪声，只防翻车。
   `--save-every N` 额外存周期性检查点到 `models/_ckpts/`。
2. **选点在训练外做**：`scripts/score_checkpoints.py`。

```bash
# 共用牌池 + 共用对手，给一批检查点排真实名次（锚点为 dushan_big_s11）
python scripts/score_checkpoints.py \
    --ckpts dushan_big_s9,dushan_big_s10,dushan_big_s11 \
    --anchor dushan_big_s11 \
    --ref "dushan_big_s7|teacher:tenpai_rush|teacher:balanced" \
    --deals 600 --out reports/checkpoint_ladder.json
```

设计要点：**同一副牌、同一批对手**（对手种子只由「第几副 + 第几个座位 + 对手名」
推出，与检查点无关），每副牌让检查点把 4 个座位各坐一遍再取均值。
于是「同一副牌上两个检查点的分差」是配对观测，比较才有分辨力。
注意 `duel.py` 把座位序号混进了牌 seed，四轮实际吃的是四副不同的牌——
只加噪声、不产生偏倚，但不是真正的复式；`score_checkpoints.py` 用同一个 seed
只换座位，是修正后的版本。

配套的 `scripts/analyze_selection.py` 把天梯当"真值"，反过来检验那些便宜的
训练内指标（胡牌率/点炮率/黄庄率/胡时均番…）与真实强度的秩相关，
并回答"如果当初用某个指标选点，会选中谁、它在天梯上排第几"。

**单元测试**：`tests/test_selection.py` 覆盖 `choose_final` 的三条分支与
配对汇总口径（含"40 副下 0.3 分的真实差距判不出显著"和"CI 随样本量按 √n 收缩"）。

## 6. 全策略循环赛：胜率分布

`arena.py` 回答的是"**我**打某个对手胜率多少"（1 打 3 个同一对手）。
想知道"**九个策略混在一桌时谁的胜率更高**"，那是另一个问题，用 `roundrobin.py`：

```bash
python scripts/roundrobin.py --reps 10        # 5040 局，约 165 秒
python scripts/analyze_roundrobin.py          # 汇总 + 配对 t 检验
python scripts/make_winrate_report.py         # 渲染自包含 HTML 报告
```

参赛：`random`、`bc`（行为克隆）、`rl`（自我对弈强化）+
六种启发式教师（均衡 / 激进 / 保守 / 囤幺鸡 / 抢听牌 / 赌徒）。

### 6.1 实验设计：为什么不是随便抽 4 个

1. **全覆盖区组**：9 个策略取 4 个上桌，组合数 C(9,4)=126，把 126 种组合**各打一遍**。
   于是每个策略出场次数完全相同（各 56 次/轮），**任意两个策略同桌次数也完全相同**
   （各 21 次/轮）——配对比较不会被"谁跟弱鸡同桌多"污染。
2. **真·复式**：同一组人用**同一副牌**轮换 4 个座位。牌墙与庄家都由 seed 决定、
   与 agent 顺序无关，所以确实是同一副牌。
   *（修正记录：`arena.py` 把座位偏移混进了 seed，四轮实际吃的是四副不同的牌，
   "复式"名不副实；`roundrobin.py` 里改为偏移只影响座位、不影响牌。）*
3. **多轮重复**：126 组 × 4 座位 × 10 轮 = 5040 局。

### 6.2 实测结果（5040 局）

| 排名 | 策略 | 胡牌率 | 每局得分 | 自摸率 | 点炮率 | 黄庄率 |
|---|---|---|---|---|---|---|
| 1 | **RL 模型** | 15.49% | **+0.527** | 12.41% | 1.83% | 47.4% |
| 2 | **BC 模型** | 14.29% | +0.415 | 11.56% | 2.23% | 48.9% |
| 3 | 教师·抢听牌 | 15.54% | +0.275 | 11.92% | 2.90% | 48.0% |
| 4 | 教师·均衡 | 12.01% | +0.203 | 9.46% | 2.10% | 52.2% |
| 5 | 教师·囤幺鸡 | 14.20% | +0.147 | 10.80% | 2.19% | 48.3% |
| 6 | 教师·激进 | 12.54% | +0.085 | 10.76% | 3.53% | 50.4% |
| 7 | 教师·保守 | 12.46% | −0.045 | 9.91% | 2.14% | 50.7% |
| 8 | 教师·赌徒 | **15.67%** | −0.075 | 13.30% | 2.54% | 48.1% |
| 9 | 随机出牌 | 0.40% | −1.531 | 0.27% | 2.72% | 55.7% |

三条结论，按可信度排序：

1. **随机策略是另一个物种**：胡牌率 0.40%，每局 −1.531 分（其他所有人都在 −0.05 ~ +0.53）。
   与每个对手的 t 值都在 8 以上。**其余八种策略在这个尺度上可以看成"都会打"。**
2. **网络确实最强，但优势远没有想象中大**：RL 每局 +0.527 排第一，
   可是跟 BC 的差只有 +0.195（t = +0.76），**统计上分不开**。
   只有对上赌徒（+0.811, t=3.64）、保守（+0.886, t=3.43）、激进（+0.523, t=2.18）
   三个教师才勉强显著。
3. **中间八种策略的名次基本是噪声**：从 RL 到赌徒，相邻名次的差异 t 值全部小于 2。
   5040 局还分不开，说明它们实力接近，名次先后不该被当真。

另外两个有意思的现象：

- **胡得多 ≠ 赢得多**。赌徒胡牌率最高（15.67%）却是负分——它 noise=9.0、
  `gang_aggression=1.5`、`safety=0`，抢得快但番数低、且点炮率不低（2.54%）。
  抢听牌同理（15.54% 胡牌 / 仅 +0.275 分）。RL 胡得没它们多，但每局赢最多。
- **"囤幺鸡"老师没抢到冲锋鸡**。它的冲锋鸡率只有 7.41%，其余教师 15%~28%。
  这恰好验证了权重设计：`keep_yaoji=6.0` 让它舍不得打幺鸡，于是拿不到"抢先打出第一张幺鸡"的冲锋鸡。

完整报告见 `reports/winrate.html`（自包含，内联 SVG，断网可开）。

### 6.3 口径

- **胡牌率**＝该策略胡牌局数 ÷ 参赛局数。四人麻将有黄庄（实测约 50%），
  所以四家胡牌率之和约 2.5，**不存在"胜率总和为 1"**。
- **每局得分**是零和量，四家之和恒为 0，可直接读作"相对平均水平的净赢分"。
- **标准误按"复式牌组"聚类**，不是按单局算：同一副牌打 4 次不是 4 个独立观测，
  按单局算会系统性低估区间。
- 策略本身是确定性的（网络 `temperature=0`），所以区间反映的是**牌运与座位波动**，
  不含策略自身随机性。要测的是"这套策略有多强"，不是"有多不稳定"。

## 7. 网页版人机对局（你 vs 模型）

不用装任何东西：启一个纯标准库的本地服务，浏览器打开就能打，**每个座位可以单独配置**
用哪个模型 / 教师 / 随机出牌。

```bash
python web/server.py                 # 默认 http://127.0.0.1:8765
python web/server.py --port 9000 --threads 4
```

界面是**相对视角**的固定牌桌：你永远在下家（下方），右 / 上 / 左依次是下家、对家、上家，
和状态编码的 `(p - me) % 4` 完全一致。左下角能看到自己的手牌，摸到牌后**点一张就打出去**；
该碰 / 该杠 / 能胡时，动作按钮会自己冒出来（只有"过"可选时会自动过，省得每次点）。
右侧是牌局记录和本局得分。

**「让模型替我想一步」**：轮到你决策时点这个按钮，`rl.pt` 会对当前局面给出 Top-3 动作
和概率，外加它对该局面的估值（正数偏有利）。这是"看看模型到底怎么打"最直接的入口，
也是自查的好工具。

### 7.1 接口

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/` | 牌桌页面（单文件 HTML） |
| `GET` | `/api/meta` | 可用模型、教师风格、27 种牌的中文名 |
| `POST` | `/api/new` | 开新局：`{opponents:[3 个配置], my_seat, seed, speed}` |
| `GET` | `/api/state?sid=` | 对局快照（前端轮询） |
| `POST` | `/api/act` | 提交动作 `{sid, kind, tile}` |
| `GET` | `/api/hint?sid=` | 模型建议（Top-3 + 局面估值） |
| `POST` | `/api/next` | 本局结束后开下一局 |
| `POST` | `/api/quit` | 结束会话 |

对手配置形如 `{"type":"model","model":"rl"}` / `{"type":"model","model":"bc","temperature":0.6}`
/ `{"type":"teacher","style":"gambler"}` / `{"type":"random"}`。

### 7.2 实现要点

**为什么不能直接用 `ZhuojiGame.play()`**：它是"起手到终局"的整体循环，插不进人类玩家。
所以 `web/server.py` 自己写了主循环——每轮只调一次 `game.step()`，人类玩家用一个
**阻塞式 Bot**（`HumanBot`）实现：

```
游戏线程:  actor = game.actor()
           action = bots[actor].choose(game)   ← 人类 Bot 在这里阻塞
                          ↑
前端提交 ──  POST /api/act ── 放进 legal_now 里匹配到的那个 Action ── 唤醒
```

好处是**规则引擎一行都不用改**：`HumanBot` 只是 `Bot` 的一个实现，
和随机 Bot、教师、网络 Agent 在引擎眼里完全同构。

其余几条约定：

- **不泄露隐藏信息**：快照里对手只给 `hand_count`，不给手牌内容；鸡牌只给"幺鸡恒为鸡"
  这条公开信息——第二只鸡要胡牌后翻牌才知道，引擎里 `_chicken_tiles()` 是按当时的
  牌墙位置算的，所以**不能在局中提前暴露**。
- **只接受合法动作**：`/api/act` 拿 `(kind, tile)` 去匹配 `game.legal_actions()` 里的
  对象，匹配不上就拒绝。前端没法构造引擎不认识的动作。
- **两手兜底**：人类 900 秒不响应自动"过"；单局超过 3000 步强制收尾。
  两条都是防止一个卡住的会话把游戏线程永久占住。
- 每步之后重建快照并加一个可调的延时（界面上的"出牌节奏"），否则机器对手会瞬间打完一整局。

### 7.3 自检

```bash
python web/server.py --selftest 40   # 自动对局 40 局，断言"必须终局 + 必须零和"
python tests/web_smoke.py            # 端到端：真起服务、真 HTTP、扮演人类打完一局（21 项）
python tests/bench_web.py            # 性能分诊：引擎耗时 vs 模型推理耗时
```

`web_smoke.py` 会把服务当成黑盒：验证页面能开、模型列表正确、快照确实隐藏了对手手牌、
非法动作被拒、人类能把一局打完、结算零和、能开下一局。

性能实测（i5-11320H / 4 线程）：**规则引擎 0.01 s/局，模型单次决策 1.1 ms，整局 31 ms**
——所以"机器对手慢"从来不是瓶颈，慢一定是因为别的（本项目就踩过一次：
自检线程卡在"等下一局按钮"上，被误判成引擎死循环）。

## 8. 独山麻将扩展（DushanMajiang 接入）

在捉鸡套件之上新增了**独山麻将**（贵州独山）完整支持，规则口径全部从
用户的 `DushanMajiang-main` 工程（rule.py / game_manager.py / settings.py）
逆向提取并逐项对齐。

### 8.1 规则要点（与捉鸡的差异）

> 📖 **完整教程见 [`docs/独山麻将规则教程.md`](docs/独山麻将规则教程.md)**
> （也可双击 `docs/独山麻将规则教程.html` 阅读）。
> 下面是摘要；凡与教程不一致处，**一律以教程/代码为准**。

- **通行证制度**：点胡必须持有通行证——杠、报叫、**胡牌张能成非平胡牌型**三者居一即可
  （按「这张胡牌张」逐张判定，不是按整手牌）。
- **报叫**：打出首张后已听牌即自动报叫（**+13 鸡**、获通行证、不可再碰杠）。
- **点炮牌归属**：点炮/热炮的那张牌归胡牌者（从打出者弃牌区移出并入赢家手牌）；
  该张若为鸡牌，其鸡分一并转给胡牌者（记「捉炮鸡」）。
- **一炮多响**：一张牌可同时点炮多名听牌者，各赢家均获得该牌并各自赔付结算。
- **抢杠胡**：只有**补杠**可被抢（自杠/明杠不能抢），无视通行证，被抢者**鸡分全烧**。
- **热炮**：杠后打出的第一张被胡，无视通行证，放热炮者**鸡分全烧**。
- **鸡**：1 条恒为鸡；**手中/副露**鸡每张 +1（金鸡 ×2）；**打出**的鸡全算——
  冲锋鸡 +3 / 横鸡 +2（按牌种独立成轮，**轮内其他家跟打同种鸡同样算横鸡**；开轮者或
  轮内已跟打过者再次出牌即收口，收口后该种鸡按普通鸡）/ 普通鸡 +1；被碰/杠走的鸡牌
  **转移**给碰杠者（计入其手中鸡，对所有人有效），打出者另赔溢价（碰冲锋 5 / 碰横 4 /
  杠冲锋 9 / 杠横 8，仅当事两人）；未听牌者按「已亮明的鸡」（打出的鸡 + 副露鸡牌）包赔。
- **翻鸡**：胡牌后翻墙顶，上下鸡（±1 同花色）皆算；翻到 2 条/9 条为金鸡（幺鸡分 ×2）。
  另有可选的**开局翻鸡**（翻牌墙尾**不移出**，只打开查看，本局仍可能被摸到）。
- **杠分 3**：明杠由点杠者付、暗杠/补杠三家各付；只有听牌者的杠计分，终局才结算。
- **黄庄**：**鸡与杠一律不结算**，只做「未听牌者 → 听牌者」的
  `自摸分 + 最大牌型分` 包赔（听牌者之间不结算）；庄家连庄。
- **牌型分叠加**：平胡 0 / 大对子 5 / 小七对 10 / 清一色 10 / 单吊 10 /
  龙七对 20（须**所听/所胡的那张**凑成四张同牌，否则算小七对；单吊与大对子互斥）。
- **胡牌方式分**：自摸 +3、点炮 +3、杠上开花 +5、抢杠 +3、热炮 +5、
  报叫胡牌 +13（自摸三家各付，点炮/抢杠/热炮由放炮方独付）。

规则引擎：`zhuoji/dushan.py`（`DushanGame` 继承捉鸡 `ZhuojiGame`，动作空间完全一致，
捉鸡预训练模型可无缝热启动）。测试：`tests/test_dushan.py`（30 项机制测试全过）。

### 8.2 网页对局（独山版，推荐入口）

```bash

# 浏览器打开 http://127.0.0.1:8770
```

- **美术资源全部来自 DushanMajiang 工程**：76×118 实体牌面 PNG、桌布、

- **大师教练**：一键获取 Top-3 推荐出牌，含概率条、局面估值、
  中文理由（鸡分机会 / 叫牌类型 / 生张风险）。
- **结算页**：总览（四家手牌/鸡牌/标签）+ 单人视角**合并大表**
  （5 列 = 玩家名｜项目｜说明｜积分｜汇总分，首末两列无表头、宽度自适应：
  逐对手明细 → 各对手「小计」行（空一行隔开）→ 末行「本局总计」；
  项目按责任方命名——包鸡/包杠等赔付项记在**付款方**名下，
  点炮分捉炮/放炮）；鸡类五项分值均可在设置里调。
- **时间类设置可自由填写**：超时自动操作 / 推荐出现时间 / 推荐上浮时间
  都是数字输入框（可填任意秒数、支持 0.5），旁边给「立即 / 自动 / 关闭」
  等常用档一键切换；推荐上浮 `-1=立即、0=自动（取超时时间的一半）`。
- **新摸的牌单独摆右**：刚摸进的手牌不插入排序位置，而是在手牌最右侧
  隔开一小段显示（带金边高亮），出牌后回到正常排序位置。
- **数据面板**：历史累计（胜率/自摸/点炮/包鸡/冲锋鸡）+ 本会话四家明细，
  对局记录 jsonl 落盘（`web/static/records.jsonl`），断线自动续局。

### 8.3 训练与防坍缩

独山 RL 从捉鸡 `rl.pt` 热启动。首轮过夜训练中复现了一次**熵坍缩**
（H 1.29→0.006、KL 2.5、评测转负），根因是 A2C 对同批样本重复 2 个
epoch 的离线过度优化。已在 `scripts/selfplay.py` 加入三层防护：

1. **每轮只更新 1 个 epoch**（消除同批数据重复优化）；
2. **自适应系数**：KL 超过目标 → 加大 KL 锚定；熵低于下限 → 加大熵奖励
   （`--kl-target 0.25 --ent-floor 0.45`）；
3. **看门狗**：熵 < 0.12 或 KL > 2.5 连续两轮 → 自动恢复最佳存档、
   学习率减半、重置优化器动量；同一存档二次坍缩则终止。

评测门控存档保留：只有复式评测平均分超过历史最佳才写存档，
"master" 模型别名自动探测 `dushan_master → dushan_s1 → dushan_s2 → rl`。

**两段训练后的实测裁决**（150 副牌复式，四家混战 vs 教师）：

| 策略 | 平均分 | 胜率 |
|---|---|---|
| rl.pt（捉鸡热启动原版） | +0.67 | 17.5% |
| dushan_s1（独山专训 1200 轮） | +0.03 | 14.7% |
| dushan_s2（精训 900 轮） | −0.18 | 11.5% |
| 教师·均衡 | −0.52 | 12.0% |

三者统计上难分高下（SE≈0.4，差距 <2 SE），全部显著强于教师——
与捉鸡循环赛结论一致：202K 参数的小模型 + CPU 预算下，
RL 微调收益在噪声量级。按实测把 rl.pt 定为 `dushan_master.pt`
（"大师"对手），独山专训版保留为可选项。

### 8.4 向量化采集与 28,000 局大型循环赛

**向量化管线**（`zhuoji/vcollect.py`）：引擎零改动，在调度层用"步进锁存"
——N 局同时推进，把所有网络决策点合成一个 batch 一次前向
（batch=64 时单样本推理 0.86ms→0.041ms，21 倍）；配合 `fan.py`
胡牌/听牌预计算缓存（热点占 27%），整体采集提速约 3 倍，
多进程再乘 ~1.4 倍。`selfplay.py --vectorized --workers N` 启用。

**八策略循环赛**（`scripts/tournament.py`，70 桌 × 100 副 × 4 轮换 =
28,000 局复式赛，每策略 14,000 局样本，SE≈±0.04，仅 4.4 分钟跑完）：

| 排名 | 策略 | 平均分 | 胜率 | 自摸率 | 点炮率 | 胡时均番 |
|---|---|---|---|---|---|---|
| 1 | bc（模仿学习） | +0.60 | 15.7% | 11.5% | 2.9% | 4.33 |
| 2 | dushan_s1 | +0.50 | 16.3% | 12.0% | 3.5% | 4.51 |
| 3 | rl | +0.47 | 15.9% | 12.2% | 3.4% | 4.24 |
| 4 | dushan_s2 | +0.35 | 14.1% | 9.9% | 3.2% | 4.80 |
| 5-7 | 三种教师 | +0.28/+0.27/+0.01 | 12.6-14.5% | — | — | ~4.3 |
| 8 | random | −2.48 | 0.4% | 0.1% | 4.1% | 10.38 |

大样本结论：四个网络显著强于教师、远强于随机；bc/s1/rl 同处第一梯队
（互差 ≤2σ）。此前 150 副小样本中"rl 名义最强"是大样本下的噪声。
风格画像：s2 均番最高（4.80）但胜率最低——激进做大牌吃亏；
保守教师垫底——独山规则下纯防守行不通。详见
`reports/循环赛报告.md` 与 `reports/tournament_results.json`。

## 9. 已知局限

- 自产数据的上限受启发式教师水平限制；BC 之后的 RL 才能超越教师。
- **统计功效不足**：捉鸡单局得分方差很大，而本套件在纯 CPU 上跑，评测规模是
  "每张桌数百副牌"。这个量级只够判断"是否碾压随机基线"这种大效应；
  想分辨 RL 与 BC 之间 0.2 分级别的差距，需要把 `--rounds` 提高一个数量级
  或改用逐副牌配对比较。
  第 6 节的循环赛把规模提到 5040 局、并用逐副牌配对，
  结果仍然只能确认"网络 > 赌徒/保守/激进"以及"所有人都 > 随机"：
  RL 与 BC 之间、以及中间八种策略彼此之间的名次差异**都还没到显著**。
  这不是实验做错了，而是这个差距本身就在噪声量级上——
  要断言"RL 比 BC 强"，得把局数再上一到两个数量级。
- 未实现报听 / 杀报（`enable_baoting=False`）。
- 未做对手建模（对手手牌推断）与 MCTS 搜索，纯策略网络直出。
- 训练在 CPU 上完成，模型规模刻意压小；换 GPU 可显著放大。
