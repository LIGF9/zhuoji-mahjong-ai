# 判读并行化：实测与用法

> 起因：2026-10-13 09:00–10:20 的 S1 段末判读，被观察到「CPU 只占 20% 左右」。
> 本文记录实测口径、根因、修法与验证。

## 1. 现象与口径澄清

| 读法 | 数值 |
|---|---|
| 你在工具里看到的 | **≈20%** |
| 进程实际占用 | **0.26 核**（12 s 采样 / 28 逻辑核）= 整机 **0.9%** |
| 全场平均（1557 s CPU ÷ 7930 s 墙钟） | **0.196 核** |

两者不矛盾：**你看到的 20% 是「单核占比」**（0.2 核 ÷ 1 核 = 20%），
换成整机口径就是 1% 不到 —— 也就是 **27.7 个核在闲置**。

代价：S1 判读 139.6 分 + vs master 配对比 38.4 分 = **178 分钟纯等待**。

## 2. 根因（两处，都不是「算力不够」）

### 2.1 单进程串行
`score_checkpoints.py` 原本是「一副一副地打」的单进程循环。

### 2.2 torch 多线程是**负优化**
同一负载，改 `--threads`（每局毫秒，越小越快）：

| threads | ms/局 |
|---|---|
| **1** | **44** |
| 8 | 75 |
| 24 | 90 |

原因看 profile（2 副牌）：`nn.Module._call_impl` 被调 **10192 次**，而单次
`conv2d` 只有几十微秒 —— 负载是「小张量 + 海量 Python 调用」，线程同步开销
远大于收益。conv2d 只占 30%，其余全是逐调用的 Python 开销。

**结论：并行度必须放在「进程 × 副牌」这一维，而不是线程。**

## 3. 修法

`score_checkpoints.py` 增加按副切分的进程池：

```bash
--workers N        # 0 = 自动（= min(CPU 核数, 16)），默认 0
--worker-threads   # 多进程时每个 worker 的 torch 线程数，默认 1
```

* **为什么不改调用方**：`m1_autopilot.py` 在内存里跑，改它对已启实例无效；
  而 `m1_segment_judge.py` / `score_checkpoints.py` 是**每次现读磁盘的子进程**。
  所以把「自动并行」做成 `score_checkpoints.py` 自己的默认 —— 托管链上
  （judge 的配对赛 + vs master 配对比）无需任何改动即自动走快路。
* **为什么默认自动安全**：第 r 副牌只依赖 `seed0 + r*1013` 与「对手名 + 第几副
  + 哪个座位」推出的种子，**副与副之间零共享状态**，因此按副切分不改变任何数值。
* 每个 worker 常驻 ≈0.45 GB（6 个模型全载入），16 个 ≈7 GB。

## 4. 验证

### 4.1 等价性（关键）
`--workers 1` vs `--workers 16`，同一牌组（master + 2 个 m1 存档）× 20 副：

* `rows` 逐字段相同 ✔（含 level / ±CI / verdict）
* `per_deal` 逐副逐模型完全相同 ✔
* **最大逐副绝对差 = 0.0** ✔

### 4.2 回归闸门
新增 `scripts/score_parallel_check.py`（退出码 0 = 通过），**7/7**：

```
PASS  两个产物的 run 元信息一致
PASS  rows 逐字段相同                        dushan_big_s11 +0.000; dushan_big_s4 -1.958
PASS  per_deal 逐副逐模型完全相同             2 模型 × 6 副
PASS  最大逐副绝对差 = 0                     max|Δ| = 0.0
PASS  并行路径确实记录了 workers             workers=4
PASS  牌组有分辨力（存在非零分差）            最大分差 6.000
PASS  锚点行恒为 0
```

> 最后两条是「守闸门的闸门」：最初一版误用了 master 与 big_s11（其实是同一份
> 权重），分差恒为 0 —— 那样等于空跑。

### 4.3 加速实测（真实牌组：6 模型，同 S1 判读配置，40 副 = 960 局）

| workers | 用时 | 加速 | 每局 | 外推 1200 副 |
|---|---|---|---|---|
| 1（旧行为） | 4.11 分 | 1.0× | 256.9 ms | **123 分** |
| **16** | **0.57 分** | **7.2×** | 35.6 ms | **≈17 分** |
| 24 | 0.59 分 | 7.0× | 36.9 ms | ≈18 分 |

**上限说明**：16 与 24 进程几乎无差 —— 这台机是 8P + 12E，E 核吞吐明显更低，
聚合有效吞吐约 7 个 P 核当量。**再加进程数只增开销。**

### 4.4 对托管链路的净效果
| 阶段 | 改前 | 改后（预计） |
|---|---|---|
| 段末判读（1200 副 × 6 模型） | 139.6 分 | ≈17 分 |
| vs master 配对比（1200 副 × 2 模型） | 38.4 分 | ≈6 分 |
| **每段合计** | **≈178 分（3.0 h）** | **≈23 分** |

S2 + S3 两段合计省下 ≈5 小时。

## 5. 用法

```bash
# 默认：自动并行（推荐）
python scripts/score_checkpoints.py --ckpts a,b,c --ref "teacher:balanced|..." --deals 1200

# 指定并行度 / 关掉并行（复现历史单进程数值，逐位一致）
python scripts/score_checkpoints.py ... --workers 8
python scripts/score_checkpoints.py ... --workers 1 --threads 24
```

* `--workers 1` 时 `--threads` 才生效；多进程时 `--threads` 被忽略。
* 回归闸门：`python scripts/score_parallel_check.py`（约 25 s）。

> 保留的证据：`reports/_tmp_judge_parallel/`（等价性、扩展曲线、真实牌组的原始 JSON）。
